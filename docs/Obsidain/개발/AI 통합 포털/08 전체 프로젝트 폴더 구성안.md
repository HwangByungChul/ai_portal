# 전체 프로젝트 폴더 구성안

> [!important] 현재 프로젝트 기준
> 새 프로젝트는 `/Users/jwpios/antigravity/202610_AI 플랫폼`이며, 이후 정식 산출물은 이 Vault 바로 아래의 단계 폴더에서 관리한다. 아래 이전 저장 위치·폴더 제안은 과거 기록이다. 현재 구조는 [[00 프로젝트 안내]]를 우선한다.

## 권고안

GraphRAG AI Agent의 **단계별 산출물 체계와 문서·소스·시험 분리 방식**을 이어받는다. BNK의 기존 제안·설계 자산을 유지하면서 단계 산출물은 현재 Obsidian Vault 안에 한 번만 저장한다. 사용자 포털·관리자·Gateway·GraphRAG는 산출물 주제와 소스 모듈로 구분한다.

현재 문서는 **폴더 생성 전 제안**이다. 아래 신규 디렉터리·소스·시험 파일·배포 구성은 아직 생성하지 않았다. 기존 파일을 재배치하지 않았다.

### GraphRAG와 달라지는 부분

- `01.docs/01.산출물`의 단계 구조는 유지하되 BNK에서는 **Obsidian Vault 안에 배치**한다. 프로젝트 루트에도 같은 문서 복사본을 두지 않는다.
- GraphRAG에 병존하는 `260.테스트/280.테스트`와 `270.이행/290.이행`은 모듈시험·파일럿·통합시험·이행으로 목적과 번호를 고정한다.
- GraphRAG의 `backend/`, `frontend/`, `src/common_core`, `tests/`, `tools/` 분리를 따른다. 실제 backend 코드와 common_core의 같은 검색 기능을 이중 구현하지 않는다.
- `common_core`는 재사용 기준선·버전·수정 이력을 기록해 도입한다. 이 구조안은 복사 또는 Git submodule 선택을 확정하지 않는다. 원본 GraphRAG 저장소를 이동하거나 수정하지 않는다.
- `common_core/admin`의 기존 PoC 관리자 서비스는 분석 참고 대상으로 둔다. 플랫폼의 인증·승인·사용량 관리자는 `backend/app/modules`에서 책임진다.
- 초기에 사용자·관리자 프론트는 한 프로젝트로 관리한다. 역할별 메뉴와 서버 권한을 분리하고 독립 앱이 필요할 때 추출한다.
- API G/W 책임은 초기 `backend/app/api`의 공통 처리로, AI G/W는 `gateways/ai_gateway`로 둔다. 폴더 분리가 독립 서버나 Gateway 제품 구축 완료를 의미하지 않는다.

## 개인 MVP 반복과 산출물 단계의 관계

| 반복 | 구현 기능 | 갱신할 단계 |
|---|---|---|
| 1 포털 기반 | 로그인·조직·Agent 목록·모의 채팅·기록 | 220/230/240 → 250/260 → 270/280 |
| 2 AI 통제 | 실제 모델·공통 호출·usage·한도·중지·취소 | 같은 단계에 Gateway·원장 산출물 추가 |
| 3 지식 Agent | 합성 문서·색인·DB·GraphRAG·근거·ACL | 같은 단계에 Knowledge/Graph 산출물 추가 |
| 4 운영 흐름 | Builder 설정·버전 평가/승인·게시/회수 | 같은 단계에 Agent/Approval 산출물 추가 |

100/210에서 전체 방향과 1차 범위를 세우고 기능별로 상세화한다. 모든 기능의 설계를 한꺼번에 끝낸 뒤 구현을 시작하는 방식으로 운영하지 않는다. 이번 프로젝트의 이행은 개인 개발·시연환경 기준이며 기관 운영 전환과 구분한다.

## 단계 폴더 안의 구성

개인 개발에서는 초기부터 빈 하위 폴더를 많이 만들지 않고 산출물 파일을 단계 폴더에 직접 둔다. 부속 그림·검증 결과가 생기면 `첨부/`와 `검증증거/`를 추가한다. 모든 단계에 `00 단계 안내.md`를 두어 다음 내용을 기록한다.

- 단계 목표·선행 입력·계획 산출물
- 작성중/검토중/확정/보류 상태
- 확인한 근거·구현 커밋·시험 결과 위치
- 다음 단계 전달사항·미결정 사항

예: `BNK_AI_240_010_API명세서.md`, `BNK_AI_240_020_권한데이터설계서.md`, `BNK_AI_280_010_통합테스트결과서.md`. 날짜·개정내역은 frontmatter와 변경 이력에 두고 여러 최신본을 병존시키지 않는다. 확정본은 Git 태그 또는 해당 시점의 스냅샷으로 식별한다.

## 문서·코드·시험·데이터의 경계

- 구현 단계 문서는 `250.구현`, 실제 코드는 `frontend/backend/src`에 저장한다.
- 시험 계획·결과 보고서는 `260/280`, 실행 가능한 시험은 `tests`에 저장한다.
- 질문/정답 평가셋의 원본은 `data/evaluation`, 실행기는 `tests/evaluation`에 둔다. 시험 fixture는 작은 파생본으로 원본 출처를 기록한다.
- 새 BNK 합성 데이터는 `data/synthetic`에 둔다. 이관한 과거 저작권 시연 자료와 섞지 않는다.
- `data/runtime`, `logs`, 가상환경, node_modules, 빌드 결과, 실제 `.env`는 정식 산출물·버전 관리에 포함하지 않는다. 필요한 검증 로그는 비밀을 제거한 증거만 산출물에 첨부한다.
- Python 실행환경과 의존성은 재현 가능한 기준을 정한다. GraphRAG의 venv·dist·로그를 복사하지 않는다.

## 기존 문서의 전환 방법

현재 `개발/AI 통합 포털`의 검토 문서는 출발점으로 보존한다. 단계별로 내용을 확정할 때 해당 단계에 **정식 산출물을 작성**하고 기존 검토에서 연결한다. 같은 최신 명세를 두 위치에서 편집하지 않는다.

| 기존 검토 | 정식 산출물로 연결할 단계 |
|---|---|
| 00 안내·04 경력 기반 착수안·05 기준 정정 | 100 프로젝트계획 |

2. 100 단계의 프로젝트계획서·MVP 범위·WBS 초안을 작성한다.
3. 210/220/230을 진행하며 첫 기능의 기술·요구·재사용 기준을 확정한다.
