# 경력 기반 집중 과제와 착수안

> [!important] 2026-10-04 프로젝트 기준 정정
> 현재 학습·MVP 대상은 **BNK 그룹 공동 생성형 AI 플랫폼**이다. [[개발/AI 통합 포털/05 BNK 플랫폼 기준 정정과 개인 MVP]]를 우선한다. 이 문서의 이전 화면/도메인/범위 판단은 해당 자료에 한정하며 새 플랫폼의 요구범위로 자동 적용하지 않는다.

## 경력 검토와 판단

제공 이력서에는 Java/Spring 기반 플랫폼, 관리자 포털·REST API·DB·정산/과금·OAuth 인증·CI/CD·운영 설계 경력이 기재되어 있다. 업무별 포트폴리오 p.3~4·9·13·15~17에서 관련 수행 범위를 확인했다. AI Full-Stack 포트폴리오 p.2~3·8~9에는 J-Brain 공통 챗봇/Intent Pack, AccountBook AI 파이프라인/재무 화면, React/Next.js·FastAPI·PostgreSQL·LangGraph 등의 구현 경험이 정리되어 있다.

따라서 학습 대상은 **기존 플랫폼 경험을 AI 호출·문서·서비스 정책에 확장하는 통합 운영 구조**로 잡는다. 이는 제출 자료에 근거한 범위 조정이며 프로젝트 코드·실행·운영 품질을 독립 검증한 평가는 아니다. 이력서의 개인정보·연봉·연락처는 학습 문서에 복제하지 않는다.

## 기존 경험을 연결할 분야

| 기존 경험·자료 | 포털에서 활용할 부분 | 추가 집중 과제 |
|---|---|---|
| 관리자 포털·사용자 서비스 | 사용자/관리자 화면·서버 권한 분리 | 관리자의 모델·프롬프트·한도 변경이 실행에 즉시 반영되는 정책 |
| API·연계·인증 | API 진입·인증·라우팅·요청 ID | 스트리밍·취소·AI 오류·모델 추상화 |
| 과금·정산·배치 | 사용량 원장·집계·대사 | 토큰 usage 누락·추정/확정 구분·실패 과금·동시 요청 예약 |
| CI/CD·운영 설계 | 환경 분리·비밀 관리·로그·배포 | 모델/프롬프트 버전별 품질·비용 관찰 |
| J-Brain Intent/Pack | 서비스 정의·프롬프트·실행 관리 구조 | 개인 서비스 여러 개의 공통 AI 경로·사용정책 |
| AccountBook·기타 AI 프로젝트 | AI 처리와 화면·데이터 연결 패턴 | 서비스별 토큰·비용·오류·한도 공통화 |

기존 소스에서 재사용할 후보는 인증·DB 접근·대화 모델·대시보드 컴포넌트·AI 제공자 호출 래퍼다. 재사용 시 의존성·비밀키·라이선스·권한 전제·테스트·실행성을 확인한다. 프로젝트를 통째로 복사해 다른 도메인의 금융·개인 자료를 옮기지 않는다.

## 추천 기술 기준선

**React/Vite + FastAPI + PostgreSQL**를 검토 기준선으로 제안한다. 포트폴리오에 이미 정리된 경험을 활용하고 기존 HTML을 화면 컴포넌트로 옮긴다. 첫 버전은 FastAPI 내부의 공통 진입 처리·AI 어댑터로 시작한다. 단일 모델·서비스 2개·사용자 2명·관리자 1명이다.

독립 AI 게이트웨이 실습은 기본 흐름이 동작한 뒤 LiteLLM 등 후보를 비교한다. API 게이트웨이 제품은 별도 실습으로 둔다. 초기 배포 단위는 프론트·업무 API·DB이며 기능 책임을 분리해 둔다. RAG 색인은 M2에서 추가한다. 기존 문서의 순수 HTML·SQLite 선택지는 입문 실습 대안이며 현재 경력 기반 추천에서는 이 기준선을 우선한다.

## 개인이 직접 주도할 다섯 과제

1. 서비스 카탈로그 설계: service_id, owner, prompt_version, model_alias, 상태, 사용권한을 정의한다.
2. 호출 계보 설계: portal_request_id→execution_id→provider_request_id→usage 원장이 이어지게 한다.
3. 비용·한도 설계: 사용자/서비스별 요청수·토큰·동시 실행·추정 비용·정산 상태를 분리한다.
4. 문서 권한 설계: 사용자 A/B 문서의 검색·인용·다운로드·삭제 반영을 같은 권한으로 통제한다.
5. 운영 검증 설계: 모델 오류·한도 초과·중지·취소·재시도·버전 변경을 실제 시연한다.

여기에 AI 코딩 도구를 활용해 작은 기능별 구현을 반복한다. 설계 산출물이 먼저지만, 기능별 완료는 실행 결과·실측 원장·시험으로 판정한다.

## 4회 반복 개발의 권고안

| 반복 | 범위 | 학습·검증 포인트 | 결과물 |
|---|---|---|---|
| 1 | 화면·인증·대화 저장·서비스 2개·모의 모델 | 사용자 분리·서비스 실행 계약·기록 재조회 | 실행 가능한 포털 기본 흐름 |
| 2 | 실제 모델 1개·스트리밍·관리자 usage·한도·중지 | 요청 계보·토큰/비용·실패/취소·제공자 호출 전 차단 | M1 완료 시연 |
| 3 | 합성 문서 RAG·근거·개인/공유 권한 | 문서 생애주기·검색권한·인용 정확도·근거 없는 응답 | M2 문서 시연과 평가셋 |
| 4 | 독립 AI G/W·모델 2개·프롬프트 버전·간단 승인 | 제공자 교체·정책 원장·중지·오류 처리의 동일성 | M3 통합 구조·운영 시연 |

각 반복 1~2주를 후보로 둘 수 있으나 주당 가용시간·기존 소스 재사용성·API 예산이 미확정이므로 납기 약속이 아니다. 반복 1의 실제 소요시간을 측정해 재산정한다. 업무 경험이 있다고 토큰/비용·RAG 평가를 생략하지 않는다.

## 첫 기능 명세로 정할 내용

- 사용자 화면: 로그인, 서비스 선택, 채팅, 본인 기록.
- 관리자 화면: 사용자 활성/중지, 서비스 설정, 사용량·실패 조회.
- 서비스: 일반 질문 / 문서 요약 초안. 요약 초안은 입력 텍스트로 시작하고 문서함 업로드·검색은 반복 3에서 연결한다.
- 초기 모델: 모의 어댑터 뒤 실제 제공자 한 개로 교체, 제공자 키는 서버에 보관.
- 완료 기준: A/B 자료 격리, 모의/실제 구분, 동일 실행 ID 조회, 정책 차단, 서버 재시작 후 데이터 유지.

MCP 도구 호출·금융 의사결정·자동 지급·다단계 자율 Agent는 초기 기능에 넣지 않는다. 사용자 화면의 카드가 있다고 실제 실행 기능이 완성된 것으로 표시하지 않는다.

## 추가로 필요한 입력

현재 주당 가용시간, 선호 구현 언어/프레임워크, 모델 API 보유 여부, 월 실습 예산, 추가 기존 코드 재사용 희망 프로젝트를 알면 착수 범위를 확정할 수 있다. 개인정보나 키 값을 전달할 필요는 없다. 기술 기준선은 경력 자료에 근거한 제안이며 아직 승인된 구현 설계가 아니다.
