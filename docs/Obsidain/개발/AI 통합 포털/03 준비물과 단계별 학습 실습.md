# 준비물과 단계별 학습 실습

> [!important] 2026-10-04 프로젝트 기준 정정
> 현재 학습·MVP 대상은 **BNK 그룹 공동 생성형 AI 플랫폼**이다. [[개발/AI 통합 포털/05 BNK 플랫폼 기준 정정과 개인 MVP]]를 우선한다. 이 문서의 이전 화면/도메인/범위 판단은 해당 자료에 한정하며 새 플랫폼의 요구범위로 자동 적용하지 않는다.

> [!note] 경력 반영
> 제공 이력서·포트폴리오를 검토한 뒤 경력 기반 추천을 [[개발/AI 통합 포털/04 경력 기반 집중 과제와 착수안]]에 추가했다. 아래는 공통 학습 목록이며 현재 우선순위는 AI 호출 계보·사용량/비용·정책·문서권한 검증이다. 기본 웹/API 공부는 필요한 부분만 복습한다.

## 개인이 준비할 항목

| 준비물 | 시작 기준 | 시점 |
|---|---|---|
| 학습 목표 | 포털·API·AI 호출·관리 흐름을 설명하고 시연 | 지금 |
| 개발 시간 | 주당 몇 시간 가능한지, 꾸준히 실행 가능한 시간 | 일정 결정 전 |
| 현재 개발 경험 | HTML/JavaScript, Python, HTTP, DB, Git 중 경험 | 학습 난이도 결정 전 |
| 테스트 계정 | 사용자 A/B와 관리자 C, 실제 금융정보 없음 | M0 |
| 예시 업무 | 일반 질문과 문서 요약 초안 두 개 | M0 |
| 예시 자료 | 직접 작성한 공개/개인 문서 5개·질문 10개 | M0/M2 |
| 개발 도구 | 편집기·Git·서버 실행 환경·브라우저 | M0 |
| 모델 접근 | 자신이 쓸 수 있는 제공자 API 한 개 또는 모의 응답 | 실제 호출 단계 |
| 비용 정책 | 월 API 실습 상한·요청/출력 제한·사용량 확인 | 실제 호출 전 |
| 검증 기록 | 화면·request_id·예상/실제·성공/실패·사용량 | 각 단계 |

실제 모델 계정·키가 없어도 화면→서버→DB→모의 응답·사용제한을 먼저 학습할 수 있다. 키는 개인이 서버 환경에 설정하고 채팅·화면 소스·버전 관리에 붙여넣지 않는다. 클라우드·GPU·상용 게이트웨이·MCP부터 준비할 필요는 없다.

## 배우고 바로 확인하는 8개 실습

| 순서 | 학습 주제 | 직접 할 작업 | 완료 확인 |
|---:|---|---|---|
| 1 | 화면과 HTTP | 기존 Chat 핵심 화면을 읽고 질문을 작은 서버로 전송 | 같은 입력이 서버에 도착하고 응답을 화면에 표시 |
| 2 | API·DB | 대화·메시지를 저장하고 기록 조회 | 새로고침·서버 재시작 후 기록 유지 |
| 3 | 인증·권한 | A/B/C 인증, 대화 소유권과 관리자 검사 | B의 A 대화 접근·일반인의 관리자 API 거부 |
| 4 | 모델 호출 | 모의 어댑터를 실제 제공자 한 개로 교체 | 임의의 새 질문에 실제 응답, 서버 키 사용 |
| 5 | 스트리밍·실패 | 생성 중·취소·타임아웃·부분 답변 처리 | 실패/취소 상태 저장, 무조건 재시도 안 함 |
| 6 | 운영 통제 | 관리자 요청수·토큰·응답시간·한도·중지 | 호출 이력으로 집계 재현, 한도 차단 확인 |
| 7 | RAG | 문서 5개 색인·권한 검색·답변 근거 | 타인 자료 미검색, 인용 위치 확인, 없는 내용 확인 불가 |
| 8 | 게이트웨이·서비스 | 어댑터를 독립 프록시로 바꾸고 서비스 승인/중지 | 포털 수정 최소화, 동일 정책·사용량·권한 유지 |

초보라면 1~3단계에 시간을 먼저 배정하고 화면 요소를 작게 분리한다. 웹 경험이 있으면 4~6단계의 usage·스트리밍·비용 정산에 집중한다. 백엔드/운영 경험이 있으면 7~8단계의 검색권한·모델 추상화·요청 계보를 먼저 깊게 검토할 수 있지만 M1의 격리 시험은 생략하지 않는다.

## 개인이 주도할 일과 AI 도움을 받을 일

사용자는 서비스 목적·화면 흐름·용어·사용권한·예상 답변·수용기준을 정하고 실제 동작을 확인한다. AI에게는 작은 기능의 코드 초안·API 설명·DB 설계 후보·오류 분석·시험 케이스를 맡긴다. ‘AI 포털 전체 구현’처럼 한 번에 크게 요청하면 어느 계층이 동작하는지 확인하기 어렵다.

요청 예: ‘기존 Chat 화면에서 질문을 모의 서버에 보내고 기록을 저장하는 한 흐름을 만들고, 새로고침 후 복원되는지 확인한다.’ 다음은 ‘사용자 A/B 권한을 추가하고 상대 대화 ID로 요청하면 거부되는지 확인한다.’ 모델 연결과 RAG는 그다음이다.

## 기간·비용을 정하는 방법

주당 5~8시간의 개인 실습을 가정하면 전체 M1~M3를 8~12주 후보로 배치할 수 있지만 약 40~96시간 범위의 **학습 계획 가정**일 뿐 납기·공수 보장이 아니다. 코딩 초보는 기초 공부·디버깅으로 더 길어질 수 있다. 각 단계 완료 기준을 충족한 뒤 다음 단계로 넘어간다. 첫 목표는 1~3단계의 실제 저장·권한 흐름이다.

월 API 상한은 사용자가 정하고 실제 선택한 모델 가격으로 산정한다. `요청수 × (평균 입력 토큰 단가 + 평균 출력 토큰 단가)`, 임베딩·검색·호스팅·저장은 별도 산정한다. 기존 화면의 모델명·비용·기능은 현재 사용 가능 여부나 권장 모델로 받아들이지 않는다.

처음에는 로컬 실행·합성 문서·모의 계정으로 실습한다. 외부 공개가 목표가 되면 HTTPS·실제 인증·비밀 관리·백업·로그·실제 비용과 운영 범위를 별도 점검한다.

## 권장 학습 자료와 확인일

2026-10-04 공식 문서 확인. 제품의 모든 기능이 무료라는 의미가 아니며 실제 도입 시 라이선스·현재 버전·유료 기능을 확인한다.

- [FastAPI 인증 예제](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/): 서버 인증의 구조를 배우는 자료. 예제 복사만으로 전체 포털 권한 완성이 되지 않는다.
- [LiteLLM AI 프록시](https://docs.litellm.ai/docs/simple_proxy): 통합 AI 호출·게이트웨이 후보.
- [LiteLLM 예산·제한](https://docs.litellm.ai/docs/proxy/users): DB 연결과 실제 예산 차단 조건을 확인할 자료.
- [Kong 요청 제한](https://developer.konghq.com/gateway/rate-limiting/): 일반 HTTP 요청 제한과 AI 제한의 차이를 확인할 자료.

## 다음 결정

첫 구현 범위는 M1의 로그인·채팅·기록·관리자 설정/현황으로 제안한다. 사용자 경험·주당 시간·모델 계정에 맞춰 상세 범위와 기술을 정한 뒤 구현한다. 이 문서는 학습·검토안이며 확정된 구현 설계서나 착수 승인은 아니다.
