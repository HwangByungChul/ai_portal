# 적재 초기화와 시연 실행 순서

## 적재 계약

아직 앱/DB가 정해지지 않아 실행 가능한 앱 적재기는 포함하지 않는다. 아래 순서는 후속 적재기·API 연결의 기준이다. 앱 고유 테이블에 직접 덮어쓰지 말고 BASE001 전용 공간에 매핑한다.

1. 패키지 버전과 manifest 파일 해시를 확인한다. JSON과 CSV가 같은 값인지 확인한다.
2. BASE001 전용 시연 공간을 생성한다. 초기화 대상은 해당 공간의 합성 자료로 제한한다.
3. 권리자→사용자 역할→증빙→저작물→이용계약→RV1 지분 순서로 적재한다.
4. 회원 신청 APP001은 DRAFT에서 시작해 이벤트 5건을 순서대로 재생한다. 이미 승인된 초기 업무 데이터와 신청 이벤트의 중복 생성은 금지한다. 신청 시연은 기존 P001에 연결한다.
5. FILE001/ROW001~002 사용자료를 접수하고 DEMO 코드로 매칭한다. 알려진 정답은 W001/W002다. 자동 매칭 여부는 구현된 방식에 맞게 표시한다.
6. 모의 청구·전액 입금을 연결한다. RUN001 계산 후 CSV 기대값 5행과 대사한다. 지급은 초안으로 유지한다.
7. USER-A/B/C 계정으로 각각 본인 조회와 타인 접근 거부를 확인한다.
8. RV2를 별도 승인해 RUN002 조정 2행을 확인한다. 기존 결과를 보존한다.
9. 공개/내부 지식 응답과 근거 없음·무권한 응답을 확인한다. 문서·권한·근거를 표시한다.

## 첫 시연 각본

회원 A 신청/보완 3분 → 담당자 승인·모의서명·권리 확정 3분 → 사용자료 수집·후보 검수 3분 → 10,000원과 1,001원 분배·잔여금 확인 4분 → 회원 본인 조회·타인 거부 2분 → 50:50 소급 조정·지식 근거 응답 3분. 총 약 18분의 구성안이다.

## 독립 예외 실행

예외마다 초기 BASE001 복제본을 만든다. SC002·SC014·SC019 등 선행 실행이 필요한 시나리오는 JSON precondition을 먼저 충족한다. RV2를 승인한 상태를 초기 정상 RV1 시연에 다시 사용하지 않는다. 실패용 지분·계약·누락 증빙은 기본 마스터 파일에 반영하지 않는다.

SC005는 RV1 안의 중첩만 만든다. SC020의 RV1/RV2 겹치는 효력기간은 정상 정정이다. SC006/007은 기존 파일 적재 후 재접수해야 하며 파일명을 바꿔도 해시가 같아야 한다. SC019는 성공 결과가 저장되고 응답만 실패한 상황을 만든다.

## 초기화 범위

생성된 계약·매칭·청구·분배·조정·신청·감사·질의 기록을 시연 공간 식별자로 관리한다. 다음 시연은 새 공간으로 실행하거나 그 공간만 초기화한다. 다른 프로젝트나 실제 자료를 삭제하지 않는다. 초기화 전후 원천 2건·초기 지분 5행·정정 미적용·지급 실행 0건을 확인한다.

## 데이터 검증과 앱 검증 구분

[[개발/시연/검증/데이터 검증 결과.json|패키지 자체 검증]]은 지분·금액·참조·상태 연속성·CSV/JSON·해시의 일관성을 확인한다. 앱 계산·권한·재시도·AI 품질·시연 화면 통과를 뜻하지 않는다. 앱 연결 후 [[개발/시연/02 금액 기대값과 예외 검증표]]에 실제 결과를 기록한다.
