# P270 전체 흐름 파일럿 Implementation Plan

> **For agentic workers:** 사용자 결정에 따라 현재 대화에서 순차 수행하며 단계별 결과와 다음 작업 계획을 보고한다.

**Goal:** 한 사용자가 로그인부터 문서 관리·규정 질문·근거 확인·회수까지 직접 따라갈 수 있는 시연을 검증하고, 불편·오류·남은 검증을 기록한다.

**Architecture:** 현재 frontend/backend/common_core 및 실제 PostgreSQL을 그대로 사용한다. 파일럿은 소유권과 표식이 확인된 별도 모의 DB/비공개 source-store에서 시작한다. Q20 evaluator와 화면 시연을 구분하며 사용자에게 내부 평가 정답을 제공하지 않는다.

**Tech Stack:** 기존 React/TypeScript·FastAPI·PostgreSQL/pgvector·Playwright. 새 제품·모델·의존성 도입 없이 진행한다.

**Spec:** [[200.프로젝트실행/240.설계/07 사용자와 관리자 화면 설계]], [[200.프로젝트실행/240.설계/08 검증과 재현 설계]], [[200.프로젝트실행/260.모듈테스트/01 C06 검증 결과와 V41 인계]], [[200.프로젝트실행/250.구현/20 합성 자료와 Q20 통합 검증 결과]].

## 범위·시간·준비 조건

다음 단계의 계획이다. 파일럿 실행·사용자 피드백은 아직 수행하지 않았다. 기존10/18~10/24 문서/파일럿16h와 검증4h 배정 안에서 파일럿 예비2h를 검토하며 C20h에 새2h를 기계적으로 더하지 않는다. 기존80h(조정10h 포함) 중 실제 소요를 측정한 뒤 중복 인계/시험 시간을 재배분한다. 개인 실투입 시간은 아직 미측정이다. 10/24 파일럿·10/28 기능 동결·10/31 종료 목표를 유지한다.

모의 전체 흐름과 실제 모델 준비를 분리한다. 실제 대표 평가가 blocked인 현재 상태를 화면 시연 성공으로 해소됐다고 표시하지 않는다. 현재 primary의mock/RAG비활성·500원 배정·0.19원 내부 기발생 추정·예약/unknown/키·원장을 보존한다. 새로운 real DB/초기화/새 배정으로 비용 검사를 우회하지 않는다.

| 순서 | 예상 | 확인할 결과 |
|---|---:|---|
| 1 |15분|현재 소스/증거·시험 환경·시연 계정/조직·비공개 접속 안내 준비|
| 2 |35분|관리자→사용자→수신 조직의 전체 흐름 화면 시연|
| 3 |25분|회수·조직 전환·접수 불명/중지·모바일과 오류 안내|
| 4 |20분|개인 사용 기록·불편/결함·우선순위·현재 소요 측정|
| 5 |25분|결함 수정/관련 회귀·실제 평가 준비 Gap·280 상세 계획|

## 작업1 — 시연 입력과 실행 안내

예정 생성: `src/backend/scripts/c06_evaluate.py`의 모의 등록 절차를 재사용하는 파일럿 준비 도구(필요할 때만 별도 `scripts/p270_prepare.py`), `src/frontend/tests/p270-pilot.spec.ts`, `270.파일럿적용/02 전체 흐름 파일럿 결과.md`, `260.테스트/evidence/P270-pilot/`.

- [ ] 새 시험 DB는 접두어+표식+실제 키 없음+모의 공급자 조건을 확인한다. source-store는 자기 소유 UUID 폴더이며 기존 파일을 정리하지 않는다.
- [ ] A/B·A-U1/A-U2/B-U1/A-ADM/B-ADM/DUAL 계정과 일반/RAG Agent를 준비한다. 필요 자료는 실제 업로드·Job·공유 API로 등록하고 정답 Graph INSERT는 사용하지 않는다.
- [ ] 비밀번호/쿠키/키는 비공개 안내 파일에만 저장하고 공개 시연 스크립트에는 계정 별칭과 목적만 쓴다.
- [ ] 브라우저에서 모의 실행임을 확인하고 준비 전 RAG는 사용 가능으로 표시하지 않는다. 접속 경로·시연 순서·안전한 종료 절차를 정리한다.

## 작업2 — 처음부터 끝까지 시연

- [ ] A-ADM 로그인→현재 조직 확인→문서 등록→접수됨→Job 단계/게시 확인. 등록202를 색인 완료와 혼동하지 않는지 확인한다.
- [ ] A-U1 로그인→일반 질문→완료·사용량·이력→규정 Agent 전환→자료 선택→규정 질문→본문·출처·원문 다운로드. 일반 질문에 문서 인용을 꾸미지 않는지 확인한다.
- [ ] A-ADM에서v1을B에 공유→B-U1에서v1 확인/질문→A에v2 등록→B에는v2 없음→B의 근거 버전 일치 확인.
- [ ] A의 개인 문서를 소유자만 조회하고 A-ADM 관리 목록은 비공개 제목을 숨긴다. 개인 소유자/reader 편집 UI는 현재 미제공임을 안내하고 API 시험과 화면 기능을 구분한다.
- [ ] Q20 evaluator의 정답·EV/R 식별자를 화면/모델 입력에 추가하지 않는다. 시연에서는 예상 행동을 설명하고 관측 결과를 기록한다.

## 작업3 — 제한·회수·오류와 모바일

- [ ] 공유 회수 후B의 새 질문·기존 답변/근거·원문이 차단되는지 확인한다. 화면은 현재5초/포커스/가시화 재검사이며 즉시push가 아니므로 관측 지연을 측정한다.
- [ ] DUAL A→B 전환·두탭·늦은 응답에서 이전 조직 내용이 섞이지 않는지 확인한다.
- [ ] 같은 요청 접수 확인과 명시 재시도, unknown/needs_review 안내가 실제 상태와 일치하는지 확인한다. 자동 재발사·새ID 중복 접수는 허용하지 않는다.
- [ ] 조직 Agent 중지·한도 초과 안내 후 신규 호출0을 확인한다. 기본 원장/기발생 비용을 바꾸지 않고 시험 DB에서만 검증한다.
- [ ] 모바일390폭에서 문서 선택·상태·근거·공유 조작의 넘침/읽기/터치 흐름을 확인한다. 스크린샷은 공개 화면만 사용하고 로그인 입력·비공개 제목/본문을 제외한다.

## 작업4 — 사용 기록과 결함

- [ ] 자동 브라우저 시험과 실제 사용자 직접 사용을 구분한다. 직접 사용 피드백이 없으면 '사용자 확인 대기'로 남긴다.
- [ ] 행동별 시작/종료·완료 여부·사용자가 막힌 지점·화면/서버 상태·재현 단계를 기록한다. 자동 시험 시간을 개인 개발 공수로 환산하지 않는다.
- [ ] 권한 우회·근거 오연결·자료 소실은 우선 수정하고 재시험한다. 장식·추가 파일 형식·통계는 이번 파일럿의 완료 조건에 넣지 않는다.
- [ ] 결함 수정 시 영향이 있는 모듈·해당 시연을 재실행하고 소스 SHA와 증거를 연결한다.

## 작업5 — 실제 모델 준비와280 인계

실제 RAG 평가 준비의 Gap은 현존 원장/DB 계약, real용 게시 index/mode 분리, 조직 Agent 허용 상태와 비밀 설정을 함께 검토한다. 현재 활성 DB는 지속 사용하는 표식 fixture이며 설계에 적힌 별도 `ai_portal_mvp_real` 운영 프로필과 차이를 명시한다. 새 real DB/새한도/사용0을 만들어 기존500원 배정을 우회하지 않는다.

- [ ] 기존 지속 real 원장을 사용하는 실행 프로필·준비 범위를 구체화한다. 기본 환경을 자동 전환하지 않는 현재 결정과 실제 평가 준비가 충돌하면 실행 전 변경 범위를 별도 설계 결정으로 기록한다.
- [ ] 실제 키를 시험 DB에 복사하지 않는다. 기존 승인 모델과 가격/토큰·기발생0.19원+예약을 대조하고 대표3~5질문의 최대 예약을 다시 계산한다.
- [ ] real/mock index를 혼용하지 않고, 실제 대표 평가를 수행하지 못하면 미완료 사유와 수행 조건을 그대로280에 전달한다. 필요 없는 유료 반복은 수행하지 않는다.
- [ ]280 통합 계획에 V41 필수 하위 조건 대조, 동시성/회수·진행 Job·취소/중지·지속 저장, 모의/실제 응답, 성능/재현의 미수행 항목을 구체화한다.
- [ ]270 결과에는 실제 사용자 피드백·모의 시연·실제 평가·수정/미해결을 구분한다. 290 새 환경 설치/복원과300 완료보고는 후속 단계로 남긴다.
