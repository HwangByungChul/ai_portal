# 동적 Tool 검토 접수 구현 결과

## 요청·결정
사용자의 다음 진행 지시에 따라 영속 Registry에 등록된 동적 Tool을 관리자 Tool 승인 요청 화면에서 검토 요청할 수 있도록 연결했다. 고위험/금융 side effect를 포함할 수 있는 동적 Tool은 위험등급이 서버에서 분류되기 전 승인되지 않도록 했다. 검토 요청 접수, 승인, 게시, 실행은 서로 다른 상태로 다룬다.

## 구현
- 신규 `src/backend/migrations/057_mcp_tool_review_gate.sql`은 tenant/session 권한 검사 후 등록된 최신 revision에서 canonical JSONB descriptor와 SHA-256 digest를 서버가 계산한다. endpoint URL 및 credential은 descriptor에 넣지 않는다.
- 동적 Tool 검토 접수는 기존 `portal.tool_approvals`와 관리자 Tool 승인 B목록/상세를 재사용하고 audit event를 남긴다. 고정 Tool ID와 충돌하는 ID는 동적 경로에서 거부한다.
- descriptor는 `risk_class=unclassified`, `approval_scope=registration_review_only`를 포함한다. 상세 API/UI가 승인 불가를 표시하고, API 검사와 DB trigger 모두 승인 전이를 fail-closed 한다.
- Tool 요청 UI는 동적 도구를 “동적 등록 검토”로 표시하고 위험등급 미분류·실행 불가를 고지한다. 기존 고정 Tool 흐름은 유지한다.

## 검증 및 적용 상태
- `git diff --check`는 통과했다.
- Python 소스 3개는 `python3 -B`와 내장 `compile()`로 구문 확인을 통과했다. `pytest -q tests/test_tool_workflow_review_http.py`는 14 passed.
- 백업은 migration 055 상태였다. 별도 복원 clone에서 056/057을 순서대로 적용했고 기존 56개 migration 기록/checksum과 업무 데이터 정규화 dump 지문이 보존됨을 확인했다. 적용 전후 지문은 `27b14b2a7bd53874796fd474e6effe61319ff3a8e4bc17c6edb4d4a8dcc50e6e`로 동일했다.
- clone에서 승인 차단 trigger 1개, audit RLS policy 1개, `ai_web`의 registry 직접 SELECT 및 tool approval 직접 INSERT 차단을 확인했다. clone은 검증 후 제거했고 프로젝트 전용 DB도 정상 종료했다.
- 격리 fixture HTTP 종단 간 시험에서 동적 등록→submission support 확인→검토요청→동일 요청 replay→타 tenant 상세 404→PADMIN 승인 409 차단→반려를 확인했다. 직접 DB 상태 변경 시도도 migration trigger에서 거부됐다. 관련 시험은 `tests/test_tool_workflow_review_http.py::test_dynamic_tool_registration_review_replay_and_fail_closed`이며 1 passed, 전체 파일은 15 passed다.
- 시험 중 `TOOL_RISK_UNCLASSIFIED` 응답 코드의 사용자 메시지 매핑 누락을 발견해 `src/backend/app/errors.py`에 안전 문구를 추가했다. 수정 후 종단 간 시험과 전체 승인 회귀를 재실행해 통과했다.
- Migration 057은 active fixture에 적용하지 않았다. 실제 백엔드는 `--reload` 없는 외부 관리 프로세스이고 service-control 소유 기록이 확인되지 않아 재시작하지 않았다.

## 미완료 범위
- 인증된 검토 UI 왕복은 진행 중이다. 승인된 gstack fallback browser로 `http://127.0.0.1:5174/manage/admin`을 열었고, 최초 화면에서 `ApprovalReviewPanel.tsx` JSX parse error를 재현했다. 조건부 JSX를 괄호 처리해 수정한 뒤 `npm run build:admin`이 227 modules·boundary verified로 통과했고 오류 화면이 관리자 로그인 화면으로 바뀌었다. 현재 사용자가 직접 로그인하도록 handoff했고 로그인 완료를 기다린다. 미인증 초기 요청의 401 외 오류 유무는 다음 확인에서 console을 비우고 재확인한다.
- 위험 등급과 승인 정책을 등록/관리하는 관리자 기능 및 안전한 분류 기준.
- PADMIN 승인 단계. 현재 분류되지 않은 동적 Tool은 승인이 의도적으로 차단된다.
- approved exact revision을 publish 상태와 사용자 도구목록에 연결하는 gate.
- 동적 execution adapter, 호출 전 권한 재검사, 기존 durable receipt와 audit/cost 연결.
- active fixture 적용 여부는 별도 배포 승인과 백업 절차에 따라 결정한다. 실제 사용자 브라우저 왕복 및 운영 수용은 미검증이다.

## 2026-10-18 · 관리자 로그인 장애 진단
- 사용자가 기존 테스트 계정 로그인이 되지 않는다고 보고했고, 해당 계정 사용은 허용했다. 채팅에 암호가 노출되어 해당 값은 사용·기록하지 않고 회전 권고 대상으로 처리했다.
- 읽기 전용 확인: 관리자 페이지 console에 503 응답이 있었고, API `/api/v1/health`는 200을 반환했다. `scripts/devdb.py status`는 DB `stopped`를 보고했으며 백엔드 로그에는 `127.0.0.1:55432 connection refused`가 반복됐다. 따라서 현 시점 증거는 인증 계정 오류보다 백엔드 DB 연결 불가에 부합한다. 로그인 성공 여부는 미검증이다.
- backend/admin frontend는 service_control 소유 기록이 없는 프로세스여서 종료·재기동하지 않았다. 활성 DB도 시작하거나 변경하지 않았다.
- 다음: 프로세스 소유권이 확인된 관리형 환경에서 개발 DB와 backend를 정상 기동하고, 새 임시/회전 자격정보로 인증된 UI를 확인한다.

### 후속 조치
- 사용자 테스트 계정 사용 허용 후 프로젝트 전용 devdb를 `scripts/devdb.py start`로 기동했다. 상태는 `running`이며 기존 backend/admin frontend 프로세스는 재기동하지 않았다.
- 관리자 화면은 로그인 폼으로 표시된다. 로그인하지 않은 초기 API 요청의 401은 확인되며 로그인 성공은 아직 미검증이다. 브라우저 점검 정책에 따라 암호 입력은 사용자에게 맡겼다.
- 다음: 사용자가 노출 암호를 교체하고 새 암호로 직접 로그인한 뒤 UI 검증을 이어간다.
- 재확인: 이후 별도 상태 조회에서 DB가 다시 `stopped`로 나타났다. 로그에는 종료 사유가 없어서 지속 기동 여부는 확인되지 않았다. 인증 브라우저 검증은 이 상태를 해결한 뒤 진행한다.
- 사용자 로그인 완료 알림 후 실제 Chrome 관리자 탭(`/manage/admin/tools`)을 읽기 전용 확인했다. 화면은 여전히 `관리자 콘솔 인증` 폼을 표시해 인증 성공은 확인되지 않았다. 암호 필드 값은 읽지 않았다. 로그인 왕복은 DB 지속 기동을 복구한 뒤 재확인이 필요하다.
- 후속 상태 확인에서 프로젝트 전용 devdb는 다시 `running`으로 유지됐다. 관리자 탭은 로그인 전 인증 폼을 계속 표시한다. 사용자가 DB 복구 전에 제출한 로그인은 성공으로 검증되지 않았으므로, 같은 탭에서 사용자 재로그인을 기다린다.
- 사용자 첨부 화면으로 `/manage/admin/tools`의 A-ADM 로그인 상태를 확인했다. 동적 MCP Tool 0개 표시 및 자동 생성 wizard 버튼이 보인다. 이전에 확인한 인증 폼은 다른/오래된 Chrome 세션의 화면으로 판단하며 앞선 로그인 미완료 판정을 정정한다. 연결된 Chrome 자동화 탭은 별도 탭에서 계속 인증 폼을 표시해 live session 조작은 검증하지 않았다. 등록 wizard 제출은 수행하지 않았다.
- 사용자가 새 Chrome 탭에서 직접 로그인한 뒤 인증 UI를 확인했다. Tool 화면의 목록/파싱/등록/모의 호출이 raw `fetch`로 tenant 및 CSRF 스코프를 전달하지 않아 서버가 `REQUEST_INVALID`로 거부하는 결함을 재현했다. `ToolAdminPage.tsx`를 공통 `api.request` 클라이언트로 바꿔 tenant ID, CSRF, `X-Requested-With`, credentials, 표준 API 오류 처리를 적용했다.
- 회귀 확인: 관리자 빌드 227 modules 및 `boundary_verified: true` 통과. 인증된 Chrome에서 목록 조회는 0개로 정상 표시되고, OpenAPI 샘플 Parse가 성공해 `check_loan_limit` 및 입력 스키마를 생성했다. 등록과 모의 호출은 누르지 않아 Registry 데이터는 생성하지 않았다. bundle 500 kB 초과 경고는 남아 있다.
- 변경 파일: `src/frontend/src/ToolAdminPage.tsx`.
