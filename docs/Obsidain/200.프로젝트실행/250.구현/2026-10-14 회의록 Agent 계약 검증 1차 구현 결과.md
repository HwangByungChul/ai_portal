# 회의록 Agent 계약 검증 1차 구현 결과

사용자가 [[31 업무 Agent 10종 승인 연결 상세 작업 계획]]·[[32 관리 B안 Tool Workflow 승인 화면 확장 상세 작업 계획]]의 다음 작업을 승인하면서 나머지9종은 추후 확장하도록 범위를 줄였다. 현재 범위는 AGENT_03 회의록 및 액션아이템 1종과 관리B Tool/Workflow 승인 화면이다. 기존A/A/B 디자인·브랜드·primary040 경계는 유지한다.

## 변경한 실제 파일

- `src/backend/app/use_cases/meeting.py`: strict 입력 memo/선택 회의일과 결정·미정·액션아이템 결과 schema, 원문 quote 포함 검사, 담당자/ISO 기한의 해당 근거문장 내 존재 검사, 미확인 담당자/기한 NULL, 서버 manifest/입출력 schema/검증코드 SHA를 포함한 결정적 계약 digest를 추가했다.
- `src/backend/tests/test_meeting_contract.py`: 실제 인용 성공, 빈/공백/NUL 입력 거부, 조작 인용/담당자/기한 거부, 미확인값 NULL, extra system_prompt 거부, digest 재현과 외부Tool 불필요 조건을 검증했다.
- 계획31·32: 사용자 승인 및 나머지9종 후속 범위를 기록했다.

## 검증

프로젝트 root에서 `src/backend/.venv/bin/python -m pytest src/backend/tests/test_meeting_contract.py -q`: **9 passed in 0.31s**. 순수 계약 검증이며 DB/API·모델·browser·전체 suite 성공이 아니다. 원문 존재 검사는 근거 없는 인용을 막는 기계적 조건이며 요약의 의미적 정확성을 보장하지 않는다. 상대 날짜의 자동 추정은 구현하지 않고 확인되지 않으면 미정이다.

## 구현 상태와 다음 작업

이 모듈은 아직 기존 Workflow runtime/승인 제출·parent결과 공개에 조립되지 않았다. 업무 API의 execution_ready=false는 유지하며 회의록 생성 서비스 완료로 표시하지 않는다. 나머지9종 활성화·기관Tool/여신 계산을 구현하지 않았다. 새 migration/기존 SQL 변경·primary 이행·업무seed·유료호출·운영배포는0이다.

다음은 계획31 Task1의 승인version에caseID/계약지문 봉인·현재업무head/CAS/역할검사와원자audit, 실제게시Agent→Workflow실행→결과검증→사용자조회/취소 연결이다. 이어 관리B의Tool/Workflow 제출·상세검증/비교·타인승인/반려의견·철회 UI를 순차 구현한다. 문서 readback과source SHA를 확인하며 Obsidian 앱 렌더는 미검증이다.
