## 사용자 요청과 현재 상태

사용자가 계획28의 수정 개발 진행을 승인했다. 기존 사용자 A안 업무 허브, 관리 A안 운영 홈과 B안 승인 목록·상세 구성을 유지하면서 기능과 표시의 실제 연결을 수정했다. 아래 변경은 실제 Python/SQL/React 소스 구현과 별도 시험 DB 검증이다. 기존 로컬 DB 적용, 전체 F1~F8 완료, 기관 UAT, 실제 제공자·Entra 연동, 운영 배포 완료를 의미하지 않는다.

## 040 파일 확인 및 기존 로컬 DB 적용 중단

- 현재 파일 SHA256: `49235a34ddcdb1a3c034c6ac42303cbd3bfadaddb20d3e2bf71830521e07fff4`
- 기존 DB 적용 이력 SHA256: `ca78a8d3c17ee6c104d5703a01c500edda3efcb7c398b2f6d26e2ae64c661adb`
- read_text().splitlines() 기준 169행이다. 행 수가 편집기에서 170으로 보이는 것과 파일 존재 자체는 적용 당시 바이트 일치를 증명하지 않는다.
- DB `dynamic_favorite_mutate`는 재시도 action 비교와 catalog_mutations INSERT에서 `dynamic_favorite`를 사용한다. 현 소스는 두 위치에서 `favorite`를 사용한다. `published_agent_read`의 함수 본문은 DB와 일치한다.
- 029의 catalog_mutations CHECK는 favorite/access_set만 허용한다. 현 소스의 action 값에는 수정 이유가 있지만 이미 적용한 040을 변경하면 기존 DB에는 적용할 수 없다. 정확한 원본을 확보한 뒤 수정은 별도 후속 migration으로 제공해야 한다.
- 두 action 값을 되돌린 후보, 줄 끝/LF/CRLF 변형, DB 함수 본문 기반 후보는 이력 SHA와 일치하지 않았다. 현재 Git에는 040 경로의 커밋 이력이 없으며 탐색한 로컬 백업·세션에서 정확한 원본을 찾지 못했다. 이 범위 밖 백업이 없다고 단정하지 않는다.
- 기존 DB는 000~040 총41 migration, 52표이며 041~045가 미적용이다. MIGRATION_CHECKSUM_CHANGED로 신규 적용은 원자적으로 중단됐다. source의 새 시험 DB 46 migration 상태와 혼용하지 않는다.
- 변경 전 백업 `/private/tmp/portal-remediation-backup-n73tq_73/before-044.dump`를 개인 권한으로 생성했다. 별도 폐기 가능한 DB로 복원하여 기존52표의 전행·열과41 checksum이 동일함을 확인했다. 백업 내용은 Vault에 복사하지 않았다.
- 현재 기존 DB의 이력을 UPDATE하거나 체크섬 검사를 해제하지 않았다. 신규041~045는 기존 DB에 적용되지 않았고 사용자 업무 데이터 생성·초기화·seed는 없다. 변경 코드의 기본 로컬 서비스 재가동은 아직 완료되지 않았다.
