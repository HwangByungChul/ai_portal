# 업무 평가 사례·자동 조건 검증 구현 결과

사용자 다음 작업 진행 승인에 따라 [[30 DP11-05 업무 평가셋과 자동 조건 검증 상세 계획]]을 먼저 작성하고 실제 DB/API/React 개발·검증·local 반영을 수행했다. 이전 [[30 DP11-04 시험 이력 수동 평가와 버전 비교 구현 결과]]의 수동 평가는 보존하고 자동 조건 검증을 별도 기록한다.

## 실제 기능

- 저장된 정확한 Agent version/profile과 입력 values/purpose를 묶어 본인 평가 사례를 불변 저장한다. 기대 답변 유형 answer/insufficient_evidence, 필수/금지문구 각최대10개·각200자, 기대자료 최대5개 document/version을 저장한다. 자료는 저장 profile 범위 부분집합만 허용한다. 중복/빈문구/충돌조건/잘못된자료·추가필드·NULL/과도길이 거부, 같은client_request_id와같은spec은동일receipt, 변경409.
- 본인·현재 관리/조직·저장 버전·자료 ACL을 저장/재시도/목록/상세/시험/평가/증적조회에서 재검사한다. 다른 관리자도 개인 입력·조건·평가를 열 수 없다. 사례목록은 이름/목적/시각/ID의 최소메타데이터20건 pagination이다. 상세에서만본인입력/조건을제공한다.
- 저장 사례 입력으로 기존TrialRepository.admit/worker/Gateway/예산/정산/취소 경로를 사용해 시험한다. 화면의 현재 변수값을 바꾸더라도 사례 시험은 불변 저장입력을사용한다. 동일client_send_id는기존receipt 복구. 새직접provider경로/공개draft실행을만들지않는다.
- 같은version/profile/composition/purpose의 완료시험만 자동검증한다. 진행/실패/취소/다른입력·버전은409. 서버가 literal-v1 규칙을 직접 계산하며 클라이언트가 전달한 passed/점수를 받지 않는다. 기대answer_kind, 필수문구포함, 금지문구없음, 실제결과에반환된기대document/version 여부를검사한다. 대소문자·공백은구분하는정확한부분문자열검사이며 의미적동치·업무사실정확성 판정이아니다.
- 신규 RAG 검색 후보에는 현재검증한자료binding을봉인한다. 생성답변은 기존실제근거배열을검사한다. 과거검색후보에출처가없으면기대자료검사를실패시킨다. 저장자료scope에존재한다는이유만으로결과가그자료를인용한것처럼판정하지않는다. 과거run/결과를소급수정하지않는다.
- 검증은 case_hash/result_hash/run_id/engine/checks/passed/시각과 함께불변저장한다. 같은case/run재검증은1행동일receipt이고replay도현재ACL을확인한다. 자동검증만수행할때provider호출0. 결과는조건충족/조건미충족으로표시하고수동업무평가·배포승인과구분한다.
- 실제관리화면에사례작성/저장/조회/입력적용/사례시험/완료시험선택/조건검증을연결했다. 기대자료는읽을수있는문서명/버전표기로제공하고이름조회가없으면저장선택자료순번으로표시한다. 저장접수불명은같은ID로확인하며원본편집·변수·버전전환을잠근다. 늦은응답/dirty·조직·자산변경결과를폐기한다. 표시된사례/평가결과는5초간격현재권한재검사실패시지운다. 증적상세와버전비교에도최근자동검증20건/총건수를수동평가와별도로표시한다.

API: /api/v1/admin/builder 아래 assets/{asset}/versions/{version}/evaluation-cases GET/POST, evaluation-cases/{case} GET, /trials POST, /checks POST. case/check원장은forcedRLS와capabilityRPC만허용한다. ai_web/index/meter raw표접근금지, policyexecutor도 UPDATE/DELETE금지, trigger불변. CSRF·no-store·본문32KiB·읽기window/현재세션유지. 평가용중간출력SSE·공개게시를추가한것이아니다.
