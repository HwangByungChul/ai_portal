# I250-C06 합성7버전·Q20·통합 인계

C01~C05의 서버·화면을 기존 합성 원문7버전과 평가 질문20개로 검증한다. 실제 입력/권한/저장 근거와 관측된 결과를 남기며 모의 계약 검증과 실제 모델 품질을 구분한다. 이 문서는 다음 작업 계획이며 평가 결과가 아니다.

기존 C20시간 중 C06 예비3시간을 유지한다. 개인 실제 공수는 미측정이다. 10월24일 파일럿·28일 기능동결·31일 종료, 주20시간 이상/총80시간(여유10시간 포함) 기준을 유지한다.

## 1. 환경과 안전한 데이터 구성

예정 신규: `src/backend/scripts/c06_evaluate.py`, `tests/test_c06_evaluation.py`(평가 분리·판정 경계), 필요 시 `src/frontend/tests/c06-pilot.spec.ts`. 기능 결함이 확인되면 해당 제품 파일과 최소 관련 시험을 수정하고 변경 이유를 결과에 남긴다. 기존 SQL000~016·키·계정/대화·real 원장과 평가 원본을 초기화하지 않는다.

전체 모의 평가부터 marker가 확인된 별도 시험 DB와 소유 source-store에서 수행한다. primary 기본 mock/RAG 비활성 설정을 자동으로 바꾸지 않는다. 조직/계정의 실제 API 응답 ID와 등록 receipt의 document/version/index/job를 내부 평가 mapping에 보관한다. 결과 공개 파일에는 비밀번호·키·DSN·토큰·원문/개인 인용 payload·벡터를 넣지 않는다.

A/B 조직 문서·개인 문서·공유 문서v1/v2를 manifest의 ACL 시나리오와 대조한다. 등록은 TXT/Markdown multipart API, 새 버전은 기존 document_id/expected_revision, 공유는 exact-version Grant API로 구성한다. scope·현재 역할 검사를 우회하는 Graph/Vector 직접 INSERT로 평가 정답을 적재하지 않는다.

Job completed와 publication을 별도로 확인한다. 각 원문 SHA/버전/pipeline/mode·청크/관계/근거 위치와 처리 한도를 대조한다. C02의7청크/23개체/18근거/16관계/7배치·819토큰은 이전 순수 계획 관측값이며 실제 적재 결과는 새로 측정한다. partial 문서를 임의로 complete로 바꾸지 않는다.

## 2. 평가 분리와 질문 실행

20질문은 단일 문서6·관계6·근거 부족4·권한 거부4다. evaluator의 question_id/classification/scenario/actor/active_tenant/request_fixture/expected_facts/required_evidence/forbidden_evidence/model_call_policy를 분리해서 취급한다.

Runtime에는 정상 질문과 서버가 허용한 document_refs만 전송한다. 정답·EV/R ID·필수/금지 목록을 embedding/모델 context/Graph 추출에 넣지 않는다. evaluator는 실행 후 서버 answer/evidence의 source SHA·exact quote·구간/관계와 평가 근거를 대응시킨다. 평가 원본의 execution.status=not_run은 덮어쓰지 않는다.

질문마다 actor/현재 tenant를 확인한 세션으로 전송하고 client_send_id를 고정한다. 응답 유실은 by-send/run GET과 같은 payload/ID로 복구하며 새ID 자동 재발사는 하지 않는다. 완료/insufficient/failed/blocked/권한 거부·본문 unavailable을 실제 API 상태에 따라 기록한다.20개가 모두 answer일 것을 기대하지 않는다.

판정에는 필요한 사실과 조건/상대 기한, 필수 관계·원문 근거, 금지 근거/조직/버전의 노출0, 허용되지 않은 source URL/인용0을 포함한다. 담당·기한 충돌이나 끊긴 책임 관계를 성공 답변으로 분류하지 않는다. DB/검색/정산 오류를 근거 부족으로 처리하지 않는다. Mock embedding의 계약 검증을 의미 검색 품질로 표현하지 않는다.

## 3. 공유·삭제·재시작

공유B는v1만 읽고 미공유v2의 존재/제목/사실을 보지 못해야 한다. private owner/reader와 관리자 관리 권한을 구분한다. 직접 document/version/run/evidence ID와 다운로드에서도 현재 읽기/본인 run이 강제돼야 한다.

Grant 철회·문서 삭제 후 새 검색과 과거 답변의 all-source gate를 확인한다. source 하나가 회수되면 전체 본문이 unavailable이며 허용되지 않은 근거 ordinal은 unavailable이다. 서버 source bytes·데이터 정리 상태와 원장 보존을 확인한다.

소유 API를 재시작하고 같은 접수ID/게시 버전/완료 run/근거를 다시 조회한다. 추가 provider 발사0과 native health 준비를 확인한다. 진행 중 Job의 known checkpoint/unknown 경계는 C03/C04 증거와 연결하고 새 통합 시나리오의 실제 관측 범위를 명시한다.

## 4. 최소 비용의 실제 대표 검증

먼저 실제 key/model·현재 월 원장·조직별 기존 배정·중지/unknown/slot·model/mode/dimension/pipeline을 확인한다. 대표500원 기준에서 기발생 내부 추정0.19원 및 모든 현재 예약을 제외한 범위를 사용한다. 이 값은 공급자 청구 확인값이 아니다. 프로젝트 예산3만원을 새로 소비하거나 한도를 자동 증액하지 않는다.

기존 생성 gpt-4o-mini/임베딩 text-embedding-3-small과 고정 tokenizer·가격 snapshot을 유지한다. 실제 사용 가능 여부·가격 조건은 실행 전 점검한다. 기존 예약상한을 사용하면 원문7배치×0.20원 + 질의최대20×0.20원 + 생성최대20×3.64원 = 최대78.20원의 사전 예약 예시다. 실제 비용/실제 호출 수/실행 가능 여부를 확정한 값은 아니며 자료·토큰·질문별 거부/보류에 맞춰 다시 계산한다.

우선 현재 배정이 준비된 A 범위의 대표 질문3~5개로 실제 입력/응답·근거·사용량을 확인한다. B와 전체 질문의 real 배정이 준비되지 않았다면 사용 가능으로 가장하지 않고 해당 실제 평가를 blocked/not_run으로 기록한다. 새 real 평가 DB에 사용량0/새 예산을 만들어 기존 지출을 우회하지 않는다. 실호출은 기존 승인 범위와 사전 확인 조건을 충족한 경로에서만 수행한다.

실제/모의 index와 publication을 혼용하지 않는다. usage_unknown·응답 중단·비용 초과 시 예약/중지 상태를 보존하고 자동 재호출하지 않는다. generation이 정상 종료됐지만 usage가 확인되지 않은 경우 본문과 비용 상태를 별개로 판정한다. 실모델을 사용할 수 없어도 모의 계약 검증을 계속하고 실제 품질 완료는 주장하지 않는다.
