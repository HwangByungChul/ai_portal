# T280 문서 장애 통합 검증 결과

사용자의 다음 작업 계속 진행 승인으로 **문서 저장·재처리·삭제 정리 장애 보완을 완료**했다. 전체280은 진행 중이다. 실제RAG와 호출 중지/보호 정보/상세 입력별 최종판정은 남아 있다. 다음 [[05 모델 호출 제어와 잔여 증거 대조 상세 작업 계획]]에서 이어간다.

## 수정한 문제와 결과

삭제 API가 문서 스케줄러의 제한을 거치지 않고 정리 작업을 직접 시작하고 있었다. 실제 API/PG로 두 순서를 재현했다. 색인 작업이 대기 중인데 정리가 바로 시작됐고, 반대로 정리가 대기 중인데 같은 조직의 다음 색인이 완료됐다. 반복 삭제 요청은 같은 정리를 여러 번 시작할 수도 있었다. 수정 전 두 시험 모두 실패했다.

삭제도 공통 대기열의 `notify`를 사용하고, 여러 버전·재시작 복구·반복 요청의 정리 키를 **문서 단위로 통일**했다. 접근 차단은 삭제 commit 직후 적용되며 물리 정리는 조직당1개/프로젝트2개 실행 제한 안에서 대기한다. 중앙 모델 예약/원장·현재 권한/SQL·lease/epoch 규칙은 변경하지 않았다. 현재workers1의 로컬 보완이며 분산 스케줄러 검증은 아니다.

|시험|실제 관측|
|---|---|
|색인 먼저 / 정리 먼저|다음 동일 조직 작업은 대기, 정리1회·총 embedding2회, 완료Job3개/활성slot0|
|Graph 관계 / 근거 DB쓰기 실패|Graph transaction rollback, 새 버전 미공개·이전 공개 버전 유지. Job은needs_review/색인은failed, 확정 embedding비용과chunk checkpoint 보존. 임의 재실행에서 새 발사0|

재처리 시험의 failed 상태는 기존 scoped worker 제어 함수의 claim/fail로 만들었다. 직접SQL로 상태를 덮어쓰거나 강제 상태 수정용 제품API를 추가하지 않았다. 정리 장애는 자체 임시 source-store의 version 디렉터리를0500으로 바꿔 경로 보호 검사에서 제거가 실패하도록 만들었고, 재시작 전에0700으로 복구했다. 실제 unlink I/O의 모든 오류 유형을 검증한 것으로 확장하지 않는다.

## 요구별 판정과 다음 작업

새로운 근거로 V017a·018b/d·019a/c의 하위 조건을 대조했다. 최신 추적표는143개 하위조건 중 **16 pass /127 not_run**, 상위V는삭제V019와감사V041의2개pass/39개not_run이다. 전체41개 통과가 아니다. 관련 기능/모듈 근거가 있더라도 정확한 입력 조합의 독립 최종판정이 덜 끝난 항목은not_run으로 유지했다. 제품39개 미구현이나 신규시험127개가 필요하다는 뜻은 아니다.

ACL16/상세60의 전체 필수 조합, 네 operation의 중지·정책 변경·추적, 보호 표식/늦은 관리 화면, 진짜 동시CAS·timeout, 실제 실행 프로필은 남아 있다. 다음05에 순서·예상 배정·관측·완료 결과를 구체화했다. 현재 호출 유형은 일반 생성/문서 임베딩/질의 임베딩/RAG 생성이다.
