## 1. 요청·범위·결론

2026-10-13 사용자가 추가 개발 내용 검토를 요청했다. 이전 UI 차이 검토 이후 현재 파일과 최신 작업 로그를 대조했다. 저장소에는 기존 여러 작업의 미커밋/미추적 파일이 함께 있어 git diff 전체를 이번 추가 작업으로 간주하지 않았다. 코드·기록을 기준으로 추가 범위를 식별했고 전체 기능명세서 F60 완료 수를 재산정하지 않았다.

추가 UI·기능 코드가 존재하며 TypeScript와 단위검사 일부는 통과했다. 그러나 실행 API 인증 누락, 보호 정책 HTTP 오류, 모의 제공자 자동 대체, 스트림 출력 검사 시점, 정책/감사의 비영속성 및 실제 연동 없는 표준 Agent/Workflow가 남아 있다. 작업 기록의 완료 표현은 구현된 부분 단위와 실서비스 완료를 구분하여 보완해야 한다. 리뷰 요청에 따라 이번에는 수정하지 않았다.

## 3. 우선 수정 항목

### R1 · P1 신규 실행 API 인증·조직/CSRF 검사 누락

위치: src/backend/app/tools/routes.py:20, app/workflows/routes.py:28, app/use_cases/routes.py:38. 기존 tenants.routes.context를 호출하지 않고 공통 세션/tenant/write 검사가 없는 경로로 tool/runner를 호출한다. main.py middleware는 request ID/일부 body제한이며 전역 인증 middleware가 아니다.

재현: create_app에 review-only DSN/가짜 HMAC 설정을 넣고 httpx ASGITransport로 lifespan 없이 요청했다. 실 DB/네트워크/유료 모델 연결은 없다. cookie·x-tenant-id·CSRF·Origin 없는 GET /api/v1/tools, POST /api/v1/tools/data_view_reader/invoke, POST /api/v1/use-cases/AGENT_01/execute, POST /api/v1/workflows/run 모두200. 도구는 현 코드의 정적 통계, Workflow는 input→output만 사용했다. 실행 권한·현재 활성 회원·조직 격리·호출 한도·취소/중복/감사 계약을 적용하기 전 실 연계 도구를 연결하면 안 된다.

### R2 · P1 보호 정책 API에서 존재하지 않는 ctx.role 사용

위치: app/guardrails/routes.py:77 및 같은 파일의 PUT/violations. 실제 AuthContext는 effective_role만 있다(app/types.py:12). 정상 인증 이후 ctx.role 조회는 AttributeError가 된다.

재현: DB 대신 context 함수를 실제 AuthContext(PADMIN)를 반환하는 대역으로 교체하고 get_guardrail_policies를 호출하자 AttributeError 'AuthContext' object has no attribute 'role'. 이는 가드레일 관리 API가 정상 작동한다고 인정할 수 없는 근거다. 엔진 단위시험만으로 HTTP/UI 수용을 대체하지 않는다.

### R3 · P1 실행 제공자가 모의로 대체되어 real 계약과 어긋남

위치: app/ai/routing.py:21/33, execution/manager.py:10, ai/gateway.py:32~52. GLOBAL_ROUTER의 기본 키 resolver는 항상None이며 OpenAI 키가 없으면 MockProvider를 반환한다. ExecutionManager는 주입된 기존 provider보다 global router를 우선 사용하는 Gateway를 만든다. 설정의 real mode/주입된 OpenAI provider와 router 키 resolver가 연결되어 있지 않다.

재현: GLOBAL_ROUTER.route('gpt-4o')가 model metadata는 gpt-4o, 실제 provider class는 MockProvider였다. 실제 OpenAI 호출/과금은 하지 않았다. 실모드 키 오류는 명시 실패로 처리하고 명시적 mock mode와 구분해야 한다. 모델별 tokenlimit/가격/저장출처·provider 일치 전체는 별도 검증 필요.

### R4 · P1 출력 검사 전에 스트림 전달

위치: ai/gateway.py:52~67, execution/manager.py:67~69, ai/providers.py:78. provider.generate에 기존 on_delta를 그대로 전달하고 delta는 hub.append를 호출한다. evaluate_output은 generate가 끝난 body에만 적용된다. 따라서 저장 최종답변을 마스킹/차단해도 선행 스트림의 원문 전달을 막지 못하는 코드 경로다.

이번에는 실제 SSE/PII 전송을 수행하지 않았다. 코드 경로 근거의 발견이며 end-to-end 재현은 미실시다. 안전한 스트림 버퍼/검사 방식과 final/stream 일치 검증이 필요하다. 전 과정 출력 보호 완료로 기록할 수 없다.

### R5 · P1 보호 정책과 감사가 조직별 영속 저장 아님

위치: guardrails/engine.py:141 _CURRENT_POLICY, guardrails/routes.py:29 _VIOLATIONS. 정책은 프로세스 전역 singleton이고 update에 tenant scope가 없다. 조직 PADMIN 한 곳의 변경이 같은 프로세스 전체 실행에 적용된다. 재시작 시 정책/감사는 초기화되고 worker 간 revision이 공유되지 않는다. 감사는10,000건 초과 시 오래된 항목을 삭제한다.

정책 범위를 플랫폼/조직 중 명시하고 해당 권한과 DB/CAS·append-only 감사 계약을 연결해야 한다. 실제 process restart/멀티worker 검증은 이번에 미실시다.

### R6 · P1 표준 업무 Agent/Workflow 실행이 실제 AI 추론 아님

위치: use_cases/routes.py:85 이후 output_parts, workflows/runner.py:56, tools/registry.py의 built-in handlers. 표준 Agent는 prompt와 정적도구 결과를 문자열로 조합하며 manifest system_prompt/model을 사용해 모델 추론하지 않는다. Workflow llm 노드는 provider를 resolve하지만 generate하지 않고 f-string 결과를 만든다. 도구는 정적 상품/규정/지점 통계이며 기관 시스템 연동이 아니다. 새 실행은 기존 승인 publication/Gateway permit/정산/현재자료ACL/영속 run·취소로 연결되지 않는다.

자동확정 금지 flag/문구 존재와 실제 금융 업무 품질/권한·검증 완료는 다르다. 현재 수준은 모의 계약 검증이며 10종 실업무 Agent 구현 완료·Workflow AI 실행 완료로 표시하면 안 된다. 실제 실행 연결은 R1을 먼저 보완한 뒤 진행한다.

### R7 · P2 관리자 운영 표시가 실제 데이터처럼 보임

위치: src/frontend/src/AdminHomePage.tsx:79~95/126~139/60. 호출 추이는45/65/80/90/75/20/15% 상수이고 서비스들은 API조회 없이 전체시스템정상·LLM정상연결·VectorDB정상연결을 표시한다. pending count는 limit5 목록길이를 전체 대기 건수처럼 보여주며 홈 요청은 기존 운영설정만 조회한다. 실제 장애 시에도 정상 표시는 그대로이고 동적 대기가 빠진다.

실측 API/시각·조회범위를 연결하거나 관측 불가로 표현해야 한다. 승인 목록·동적 요청과 전체 집계 연결도 보완해야 한다. HomePage의 성능개선 공지 또한 정적 문구이므로 실제 검증 근거·게시 관리 상태와 구분한다.

## 5. 실제 변경 파일·다음 작업

이번 변경 파일은 본 보고서·작업 기록02뿐이다. 추가 개발 앱코드/계정/DB/설정은 수정하지 않았다. 검토 중 테스트는 별도 프로세스와 mock/dummy 데이터만 사용했고 DB필요 시험은 fixture setup에서 중단되었다. Obsidian 파일저장/링크는 확인하며 읽기화면 검증은 미실시다.
