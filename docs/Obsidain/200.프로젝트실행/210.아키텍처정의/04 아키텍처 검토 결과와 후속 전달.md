# 아키텍처 검토 결과와 후속 전달

## 목적과 검토 상태

100 승인 계획과 210의 격리·모듈·저비용 모델 결정을 하나로 정리한다. 2026-10-04 사용자 “네”는 저비용 방향에 따라 검토를 계속할 수 있는 답변으로 기록한다. 본 종합 문서와 저장소 운영 세부 원칙까지 이미 최종 승인된 것으로 표시하지 않는다. 종합 검토 후 220으로 전환하며 앱 구현과 실제 API 호출은 아직 없다.

## 최종 검토할 구조

| 구성 | MVP 책임 | 다음 단계 입력 |
|---|---|---|
| React/Vite 사용자 포털 | 로그인·허용 조직/Agent 선택·질문·본인 대화·문서 근거 | 화면별 액터와 허용/거부 조건 |
| React/Vite 관리자 포털 | 조직 사용자/역할·문서/색인 상태·Agent 설정/중지·사용량/한도 | 관리자 조직 범위와 변경 효과 |
| FastAPI 공통 API 진입 | 인증·소속/역할·자원 접근·요청 추적·HTTP 제한 | API 우회 접근 거부 요구 |
| FastAPI 업무 모듈 | 대화·문서·Agent·작업 상태·업무 권한 | 실행 흐름과 지속 저장 요구 |
| 공통 AI 호출 + Usage/Quota | 서버 모델 설정·제한된 호출·사용량/한도 단일 원장 | 중앙 호출과 한도/중지 시험 |
| GraphRAG common_core | 문서 처리·벡터/관계 검색·근거 연결 | 기존 코어 보완 항목과 정답 근거 |
| PostgreSQL 및 파일 저장 | 조직별 데이터·개인 접근·처리 상태 지속 저장 | tenant_id·RLS·파일/Job 권한 상세 설계 |

단일 FastAPI 서버 안에서 모듈 책임을 나눈다. 별도 API G/W 제품이나 별도 AI G/W 서버를 설치하는 범위는 아니다. 일반 질의 Agent와 합성 규정/책무 RAG Agent 두 개의 고정 실행 흐름을 구축한다.

## 멀티테넌트 기준

- 공통 테이블의 tenant_id, 서버 소속/자원 권한 검사, PostgreSQL RLS를 함께 적용한다.
- 가상 조직 A/B의 문서·청크·그래프 관계·근거·대화·Job·원장을 분리한다. 같은 조직의 개인 자료도 별도 소유/허용 조건을 검사한다.
- 관리자는 허용 조직 안에서 관리한다. 명시적 자산 버전/수신 조직 Grant 없이 전 조직 검색을 허용하지 않는다.
- 연결 풀·실패/rollback·동시 요청·비동기 Job에도 조직 문맥을 유지한다. 앱 런타임은 RLS를 우회하는 역할을 사용하지 않는다.

## 실행·저장소 운영 원칙

질문은 권한 검사 → 허용 자료 검색 → 근거 조립 → 공통 모델 호출 → 응답/근거/usage 저장 순서다. 일반 질의는 검색 단계를 생략한다. 문서는 권한 검사 → 등록/Job 저장 → 파싱/청킹 → 필요한 임베딩 → 그래프/벡터 저장·검증 → 처리 상태 갱신 순서다.

실행·대화·색인 상태를 DB에 저장하고 재시작 후 유지한다. 실패하거나 중단된 색인은 완료로 표시하지 않는다. Job은 기록된 조직/주체와 자체 DB 세션으로 처리한다. 삭제·공유 회수 문서는 신규 검색·인용·다운로드에서 제외하며 과거 대화에 저장된 근거 링크도 현재 권한을 확인한다. 그래프의 공용 개체를 삭제할 때 다른 허용 근거/관계를 훼손하지 않도록 상세 설계한다.

## 저비용 모델과 범위 제한

기본 답변은 gpt-4o-mini, 문서/질의 임베딩은 text-embedding-3-small을 사용한다. 사용자 화면의 모델 선택·유료 비교·동적 가격 관리·정교한 과금 기능은 후속이다. 기본 사용량 기록·조직/프로젝트 한도·Agent 중지는 유지한다. 10월 API 합산 상한은 30,000원이며 반복 시험은 모의 모델, 실제 API는 대표 검증에 사용한다. 변경 없는 문서 재임베딩과 무제한 재시도를 방지한다. 모델 접근 가능성/응답 품질은 실제 검증 단계에서 확인한다.

## 220 요구정의에 전달할 목록

아래는 승인 계획에서 추출한 요구 입력이다. 220에서 요구 ID·액터·입출력·오류/권한 조건·시험을 구체화한다. 이 표 자체가 220 완료 산출물은 아니다.

| 입력 ID | 기능/조건 | 완료를 확인할 결과 |
|---|---|---|
| IN-01 | 로그인 및 허용 조직 선택 | 인증 실패/미소속 조직 선택 거부 |
| IN-02 | 일반/RAG Agent 선택 및 질문 | 허용 Agent만 실행, 중지 Agent 호출 거부 |
| IN-03 | 대화와 본인 기록 | 재시작 후 조회, 타인/타 조직 대화 거부 |
| IN-04 | 답변 근거와 원문 | 관계별 올바른 근거, 현재 권한의 원문 접근 |
| IN-05 | 조직 사용자/역할 관리 | 관리자 범위 제한과 변경 권한 재검사 |
| IN-06 | TXT/Markdown 문서 등록·색인 | 5~10개 합성 문서, 성공/실패 상태 구별 |
| IN-07 | 문서 삭제와 공유 승인/회수 | 신규 검색/인용/다운로드에 현재 권한 반영 |
| IN-08 | Agent 설정/중지 | 신규 실행에 설정/중지 반영 |
| IN-09 | 사용량/한도 조회 및 차단 | 단일 원장, 조직·프로젝트 한도 우회 불가 |
| IN-10 | API/AI 공통 경로 | 직접 ID/URL 우회 차단, 실제 모델 호출 중앙화 |
| IN-11 | GraphRAG 관계/근거 | 관계와 근거 연결 일치, 근거 부족 시 보류 |
| IN-12 | 동시 요청·Job·지속 저장 | A/B 문맥 혼입 없음, 오류/재시작 상태 유지 |

요구 추적은 현재 계획과 검토 문서를 근거로 한다. 원 RFP 조항 번호와의 일대일 추적은 원본 조항을 실제 확인한 항목만 표기하며 완전한 RFP 대응표라고 표시하지 않는다.

## 230/240 이후 전달

230 분석: 기존 GraphRAG의 미구현 DB/벡터 어댑터·AuthContext 권한 미적용·관계/근거 불일치·중복 검색 경로를 재사용/수정/신규로 분류한다. 기존 화면과 실제 연결 여부도 대조한다.

240 설계: 테이블/RLS·파일 ACL·API 계약·로그인 세션·Job/실행 상태 전이·Agent 설정 항목·입출력/동시 호출 제한·최소 한도 예약/원장·삭제/공유 회수·초기화/이행을 정의한다. 구현값은 이 단계에서 정하며 누락을 이미 구현된 것으로 취급하지 않는다.

250/260: 승인된 기능별 설계와 구현계획에 따라 조직/권한·포털/대화·공통 AI/usage·문서/GraphRAG 순으로 구현하고 필요한 시험을 수행한다.

## 검증과 일정 조정

평가 질문 20개는 단일 문서 6·관계 6·근거 부족 4·권한 거부 4로 구성한다. 별도로 A/B 직접 접근·개인 자료·동시 요청/Job·관리자 중지/한도·삭제/공유 회수·재시작 시험을 연결한다. 실제 시험 증거는 260/280에 기록한다.

10월 31일·4주 80시간(여유 10시간) 기준을 유지한다. 일정이 부족하면 화면 장식·통계 상세·관리 편의 기능·모델 비교부터 줄인다. 조직 격리·근거 정확성·상태/지속 저장 등 핵심 검증 실패는 미완료로 남긴다.

## 자체 검토

- 100의 사용자/관리·API/AI·GraphRAG 범위가 담당 모듈 및 요구 입력에 연결된다.
