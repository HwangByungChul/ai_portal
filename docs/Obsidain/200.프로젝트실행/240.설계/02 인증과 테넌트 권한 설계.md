# 인증과 테넌트 권한 설계

> **현재 기준 — 2026-10-04 종합 승인:** 사용자가 종합 설계 보고 후 “네 진행 바랍니다”로 후속 진행을 지시하여 이 설계를 확정했다. [[200.프로젝트실행/250.구현/01 인증과 테넌트 기반 구현 계획]]으로 전달한다. 아래 각 D240 작업 당시의 검토 대기/미수행 서술은 작성 이력이다. 현재250의A01~06 실제인증·조직관리·RLS·화면과재시작/실DB장애·복구·통합검증완료다. 첫기능A만완료이며다음B01/전체AI·Graph는후속이다. 최신결과는250.02의24~27절/B계획은250.03을따른다.

## 1. 결론·상태·입력

개인 MVP의 인증은 **서버 저장 세션 + HttpOnly 쿠키**를 권고한다. 조직 ID는 요청마다 하나를 선택하고, 서버가 현재 계정·소속·역할과 자원 소유/버전을 함께 검사한다. 관리자 역할은 개인 본문 열람이나 조직 간 우회 권한이 아니다. 역할만 검사하는 RBAC에 tenant/owner/version/Grant 조건을 결합한다.

D240-01 문서 작성과 자체 점검 완료. 사용자 “네 진행 바랍니다”로230 종합 결과 및240 순차 설계 착수를 확인했다. 이 문서는240 종합 검토에 전달할 상세 설계안이며, 인증 구현·실제 계정/DB 설정·ACL 시험 통과나250 코드 착수 승인이 아니다. 앱 src는 미구현이고 실제 시험은 미수행이다.

입력: [[200.프로젝트실행/220.요구정의/02 액터와 권한 정의서]], [[200.프로젝트실행/220.요구정의/03 사용자 포털 요구사항]], [[200.프로젝트실행/220.요구정의/04 관리자 포털 요구사항]], [[200.프로젝트실행/220.요구정의/06 요구사항과 검증 추적표]], [[200.프로젝트실행/230.분석/03 GraphRAG와 백엔드 재사용 분석]], [[200.프로젝트실행/230.분석/05 합성 데이터와 평가 기준]], [[200.프로젝트실행/230.분석/06 분석 결과와 설계 전달]].

기존 E14/E15·C02/C03의 비밀번호 미검사/자동 관리자 등록·localStorage 모의 토큰·클라이언트만의 로그아웃을 새 실행 경로에서 대체한다. 기존 E03의 선택적인 AuthContext를 요청의 필수 문맥으로 전환할 계약이다. 기존 코드는 이번 작업에서 변경하지 않았다.

## 2. 인증 대안과 선정 이유

| 안 | 장점 | 부담·제약 | 이번 설계 판단 |
|---|---|---|---|
| A. PostgreSQL 세션 + 쿠키 | 서버에서 만료/로그아웃을 바로 판정, 현재 소속/역할 조회와 함께 운영 가능 | 요청마다 세션 조회, 쿠키 사용에 따른 CSRF 방어 필요 | **권고**: 단일 웹 포털/단일 FastAPI·기존 PostgreSQL에 적합 |
| B. JWT access/refresh | 외부 API 클라이언트 확장에 유리 | 회수 목록·refresh 회전·현재 권한 조회가 여전히 필요, localStorage 보관은 사용하지 않을 것 | 이번 MVP에 추가하지 않음 |
| C. 외부 OIDC/SSO | 조직 인증 제공자와 연계 가능 | 제공자·조직 매핑·운영 설정 증가 | 승인된 후속 범위 유지 |

인증/세션은 FastAPI 공통 진입 모듈의 책임으로 두고 API G/W 제품·별도 인증 서버·Redis를 도입하지 않는다. 성숙한 비밀번호 해시/난수 라이브러리를 사용하며 암호 알고리즘을 직접 만들지 않는다. 사용할 라이브러리와 버전 고정은250 기능 구현계획에서 확인한다. Starlette의 클라이언트 서명 쿠키에 역할/조직을 넣는 것을 여기서 말하는 서버 세션으로 혼동하지 않는다.

OWASP의 세션/CSRF/비밀번호/요청별 권한 권고를 참고했다. 아래 시간·길이·차단 횟수는 표준 의무값이 아닌 **이 MVP의 설계 선택값**이다. 출처는12절에 기록했다.

## 3. 로그인·세션·로그아웃 계약

### 3.1 로그인

- 사전 생성한 합성 계정의 login_id와 password를 검증한다. 공개 회원가입·전역 계정 생성/삭제/비밀번호 재설정 UI는 추가하지 않는다. 초기화/운영 절차가 계정과 초기 관리자 권한을 부여한다.
- login_id는 공백 제거 후 소문자 ASCII 식별자로 조회하고 길이3~64자, 허용문자 영문/숫자/점/밑줄/하이픈으로 제한한다. password는 입력을 정규화하거나 잘라내지 않고 검증하며 최대128문자/UTF-8 512바이트로 제한한다. 초기 비밀번호는15~128문자로 준비하고 실제 값을 문서/저장소/로그에 남기지 않는다.
- Argon2id 해시는 salt를 라이브러리에 맡기고 최소 메모리19MiB·반복2·병렬1을 사용한다. 실제 기기에서 비용을 확인하여 이 기준 이상으로 조정한다. 미존재 계정도 동일 계열의 더미 해시 검증을 거쳐 존재 여부가 오류문으로 드러나지 않게 한다.
- 비밀번호 성공 + account.active=true일 때만 새 세션을 발급한다. 활성 조직 소속이 없으면 로그인된 상태에서 조직 없음 안내만 제공하고 업무 API를 허용하지 않는다. INACTIVE는 세션을 발급하지 않는다.
- 실패는 계정 미존재/비밀번호 오류/비활성의 같은 일반 안내다. DB 오류 시 정상 로그인으로 대체하지 않는다. 로그인 시 이름만으로 자동 계정 생성하거나 ADMIN을 부여하지 않는다.
- 인증 진입에는 login_id별15분에 실패5회 후 해당 창의 남은 시간 차단, 직접 접속 IP별15분에 로그인 시도30회 상한을 둔다. 성공해도 IP 창을 초기화하지 않는다. 영구 계정 잠금은 하지 않는다. 실패 카운터의 원자 증가/지속 저장은D240-02, 오류/응답은D240-03에 전달한다. 신뢰되지 않은 X-Forwarded-For는 IP 기준으로 사용하지 않는다.

### 3.2 세션

| 항목 | 설계 계약 |
|---|---|
| 인증 식별자 | CSPRNG 32바이트의 불투명 난수, 의미 있는 사용자/역할/조직 정보 없음 |
| 서버 저장 | 세션 내부ID·token SHA-256 해시·user_id·발급/최근 활동/절대 만료·revoked_at·계정 인증 revision·CSRF 난수. 인증 token 원문은 저장하지 않음 |
| 검증 | 해시로 세션 조회, 현재 계정 상태/revision 및 세션 유효성을 검사. role/tenant를 쿠키의 주장으로 신뢰하지 않음 |
| 수명 | 절대8시간, 업무상 사용자 행동이 없는 유휴30분. 두 만료 중 먼저 도달한 시각 이후 거부. DB UTC 시각 사용 |
| 유휴 갱신 | 성공한 사용자 업무 조회/변경만 last_activity 갱신. 상태 폴링·자동 keepalive·실패 요청은 연장하지 않음 |
| 재로그인 | 새로운 난수와 CSRF 값 발급. 같은 브라우저에서 제출된 이전 유효 세션은 회수, 이전 식별자를 승계하지 않음 |
| 브라우저 저장 | 인증 값은 쿠키로만 전달. localStorage/sessionStorage·URL·응답 JSON·로그에 넣지 않음 |
| 서버 재시작 | DB에 저장된 세션의 원래 만료/회수를 보존. 재시작만으로 수명 연장하지 않음 |

외부/원격 시연은 동일 출처 HTTPS를 전제로 쿠키 `__Host-ai_session`, Secure, HttpOnly, SameSite=Lax, Path=/, Domain 미지정으로 발급한다. 쿠키 만료는 절대8시간을 넘지 않으며 서버의 유휴/회수 판정이 우선한다. 포털/API는 동일 출처로 제공한다. 개발 시 Vite의 /api 프록시를 사용한다.

개인 기기의 loopback HTTP 개발에서만 별도 이름 `ai_session_dev`와 Secure=false를 명시적으로 허용한다. 바인딩은127.0.0.1이며 dev 설정으로 외부 공개하지 않는다. 모바일 접속/외부 시연은 HTTPS 설정을 사용한다. 두 이름을 동시에 인증 수단으로 수용하지 않고 실행 프로필에 맞는 쿠키 하나만 검사한다. HTTPS/TLS 구성은 이 문서 작업에서 실행하지 않았다.

### 3.3 CSRF와 전송

로그인은 application/json + 포털 지정 헤더 `X-Requested-With: ai-portal` 및 정확한 허용 Origin 검사로 보호한다. form/text/plain 로그인과 Origin 누락/불일치는 거부한다. 로그인의 응답에도 인증 token을 JSON으로 넣지 않는다. 새 로그인 성공 이후부터 세션별32바이트 CSRF 난수를 적용한다.

인증된 상태의 POST/PUT/PATCH/DELETE는 `X-CSRF-Token`과 서버 세션 값의 일치 및 Origin 일치를 모두 검사한다. 토큰은 인증된 본인 세션 정보 조회로 받아 메모리에만 보관하고 새로고침 때 재조회한다. 세션별 값은 유지하므로 다른 탭을 임의 무효화하지 않는다. CSRF 값은 인증 cookie와 별개이며 단독 인증 수단이 아니다. GET에는 변경/유료 실행을 배치하지 않는다. SameSite만으로 CSRF 방어를 완료했다고 판단하지 않는다.

Credential을 허용하는 광범위 CORS는 열지 않는다. CORS를 권한 검사로 취급하지 않는다. 동일 출처는 scheme/host/port를 모두 대조하며 허용 출처는 서버 설정값이다. 외부 Host/Forwarded 헤더로 허용 출처를 자동 결정하지 않는다. 세션/CSRF 응답과 개인 자료 응답은 Cache-Control: no-store를 적용한다. 구체 API 경로·오류코드·스트리밍 전송은D240-03에서 정의한다.

### 3.4 로그아웃과 회수

로그아웃은 CSRF/Origin 확인 후 **서버 세션 회수 저장 → 쿠키 삭제 → 성공 응답** 순서다. 프론트는 성공 또는 이미 만료된 세션 확인 후 사용자·조직·질문/이력·근거 캐시를 비운다. 저장 실패를 정상 로그아웃으로 표시하지 않으며, 화면은 민감 내용을 가리고 재시도를 안내한다. 이미 무효인 세션의 반복 로그아웃은 상태 변경 없이 쿠키만 정리한다. 반복 무효 세션에도 Origin/지정 헤더를 확인한다.

로그아웃 후 예전 쿠키를 복사한 신규 요청은 거부된다. 현재 브라우저 세션 회수가 다른 기기 세션을 자동 회수하지는 않는다. 계정 전역 비활성화·운영 비밀번호 재설정은 account.auth_revision 갱신으로 모든 이전 세션을 거부한다. 전역 계정 운영 UI는 이번 범위 밖이다. 소속/역할 변경은 세션의 인증을 보존하되 요청 때 현재 권한을 다시 판정한다.

이미 접수된 비동기 Job은 로그인 세션의 수명을 그대로 작업 수명으로 사용하지 않는다. 로그아웃만으로 접수 Job을 삭제/자동 취소하지 않고, 기록한 수행 주체의 현재 계정/소속·작업 권한을 검사한다. 본인 취소는 별도 업무 요청이다. 대화 실행의 취소·스트림 종료는D240-03/04에서 정의하며 로그아웃이 이미 발생한 호출 비용을 회수한다고 주장하지 않는다.

## 4. 조직 선택과 신뢰 문맥

### 4.1 요청 조직

사용자 조직 목록은 본인의 활성 membership과 활성 tenant만 반환한다. TADMIN의 관리 목록은 그 중 TADMIN 역할의 조직, PADMIN의 관리 목록은 별도로 부여된 활성 관리 소속만 반환한다. PADMIN 권한이 있다고 임의 조직을 선택할 수 없다. 플랫폼 권한과 관리 소속은 독립 조건이다.

업무 요청은 **단일 `X-Tenant-ID`**를 필수로 가진다. 유효한 UUID 식별자를 선택 힌트로 받아 현재 소속을 검사한 다음에만 신뢰 문맥을 만든다. 합성 A/B 표시명과 실제 tenant UUID의 매핑은D240-02/07에서 정의한다. 헤더 중복/누락/형식 오류는 거부하고 role/user_id를 클라이언트가 주장해도 신뢰하지 않는다. 경로/본문에 소유 tenant가 필요한 API는 헤더와 같은지 검사하며 소유자를 바꾸는 기능으로 사용하지 않는다. 공유 조회의 원 소유 tenant는 서버가 문서/Grant에서 얻는다.

세션에 전역 active_tenant를 저장하지 않는다. 탭A는 A 요청을, 탭B는 B 요청을 독립 제출할 수 있다. 프론트 선택값은 탭 메모리에 두고 매 요청/응답의 조직 문맥을 확인한다. 전환 시 해당 탭의 이전 목록/이력/근거/입력을 비우고 이전 조직의 늦은 응답을 폐기한다. 자원 소유 tenant와 DB 조회 문맥이 프론트 전환으로 변경되지 않는다.

### 4.2 요청 문맥 필드

| 필드 | 신뢰 출처·의미 |
|---|---|
| request_id | 서버 발급 추적ID. 인증/권한 대신 쓰지 않음 |
| principal_kind | interactive_user 또는 delegated_job. 외부 요청은 user만 가능 |
| session_id | 내부 세션ID, HTTP 요청에서 필수. Job은 origin_session_id를 감사용으로만 참조 |
| user_id / account_auth_revision | 현재 활성 계정과 revision. 클라이언트 supplied owner로 대체하지 않음 |
| scope_kind | tenant 또는 제한된 platform_control |
| active_tenant_id | 검증된 활성 소속의 조직. tenant 업무에서는 필수 |
| membership_id / membership_revision | 현재 조직의 활성 소속/변경 revision |
| effective_role | 현재 조직에서 USER/TADMIN, 또는 플랫폼 권한과 관리 소속을 함께 검사한 PADMIN |
| platform_permissions | 공통 집계/중지 등 명시 권한 목록. tenant 콘텐츠 조회 권한 아님 |
| action / resource_ref | 서버 라우트의 행동 및 조회된 자원ID/owner tenant/owner user/doc version |
| relevant_policy_revisions | 작업에 쓰인 문서 ACL/Grant/Agent 설정의 revision. 최신 검사 여부를 추적 |

판정 실패 시 문맥을 부분 생성하여 다음 모듈에 넘기지 않는다. AuthContext의 tenant/user/role이 비어 있거나 서비스가 현재 권한을 검증할 수 없으면 거부한다. 이 필드는 인터페이스 계약이며 실제 클래스/테이블 이름은 아직 구현하지 않았다.

### 4.3 조직 없는 경로

D240-08 통합: 플랫폼 조회 `global_usage_read`와 운영 변경 `global_stop_write`는 독립 권한이다. API-03 capability는 현재 PADMIN/해당 permission의 서버 계산값이며 UI 표시 힌트일 뿐 허가 증표가 아니다. `can_change_platform_availability=true`인 경우에만 공통 `platform_availability.enabled/revision`을 반환하여 비용 조회 없이 변경 revision을 확보한다. API-39 합산은 조회 권한만, API-40 변경은 쓰기 권한만 검사한다. 두 권한 모두 없으면 이 상태 필드도 반환하지 않는다.


health의 비민감 생존 확인, 로그인/세션/본인 소속 목록과 제한된 플랫폼 공통 제어는 조직 선택 없이 사용할 수 있다. 각 라우트의 명시한 제어 경로만 예외이며 누락 tenant를 일반 예외로 허용하지 않는다. 플랫폼 공통 조회/중지는 현재 PADMIN + 해당 platform_permission을 검사하고 합산 값/운영 상태만 제공한다. 이 경로로 개인 자료나 전 조직 행을 읽는 범용 DB 세션을 발급하지 않는다.

DB의 인증 제어 자료·플랫폼 집계와 tenant 자료의 정책 분리는D240-02가 책임진다. runtime은 superuser/BYPASSRLS/테이블 소유자가 아니며, 서비스에서 허용했다고 RLS를 비활성화하지 않는다.

## 5. 자원별 판정 계약

모든 콘텐츠 조회는 현재 계정·세션 또는 위임 주체의 유효성 → 현재 조직 소속 → 요청 행동 권한 → 자원 범위/소유/버전 → 저장소 정책 순서로 확인한다. 직접 ID·검색·Graph/벡터·파일 다운로드·캐시·근거 링크에서 같은 판정을 적용한다. 알려진 무권한 자원 요청은 질의 임베딩/생성 호출 이전에 차단한다.

| 자원/행동 | ACT-USER | ACT-TADMIN | ACT-PADMIN |
|---|---|---|---|
| 개인 문서 제목/본문/원문/근거 | 같은 조직 owner 또는 같은 조직의 명시 read 허용 사용자 | 동일 콘텐츠 ACL | 동일 콘텐츠 ACL |
| 조직 문서 조회 | 현재 조직 활성 member, published/삭제 아님 | 동일 | 명시 관리 소속 및 동일 조회 조건 |
| 다른 조직 공유 문서 조회 | 조직 문서의 **정확한 버전**·활성 recipient Grant·활성 소유/수신 조직, published/삭제 아님 | 동일, 읽기만 | 동일, 현재 수신 조직일 때 읽기만 |
| 조직 문서 등록/새 내용 버전/삭제 | 불가 | 현재 조직 관리 권한 | 명시 관리 조직에서 동일 |
| 개인 문서 초기 등록/색인/삭제 | 등록 불가, 콘텐츠 ACL 조회만 | 같은 조직의 지정 owner/허용 사용자 검증 후 등록. 최소 상태·색인/삭제 운영 가능 | 명시 관리 조직에서 동일 |
| 기존 개인 문서 내용 갱신 | 이번 일반 사용자 업로드 기능 없음 | 관리 권한 **및** 콘텐츠 read ACL 필요 | 동일 |
| 개인 문서 ACL/owner 사후 변경 | 이번 MVP에는 제공하지 않음 | 등록 후 자기 자신을 추가하거나 조직 범위로 변경 불가 | 동일 |
| 문서 버전 Grant 생성/회수 | 불가 | 현재 원 소유 조직의 조직 문서만 | 명시 원 소유 관리 조직에서 동일 |
| 수신 공유 문서 변경/삭제/재공유 | 불가 | 불가 | 수신 조직에서는 불가. 원 소유 관리 조직으로 정당하게 선택한 요청은 별도 판정 |
| 대화/메시지/답변/실행 내용 | 현재 조직 + 본인 conversation.owner | 동일 | 동일 |
| 본인 실행 취소·재조회 | 현재 조직 + 본인 실행, 현재 실행 접근 권한 | 동일 | 동일 |
| Agent 조회/실행 | 현재 조직 허용 고정 Agent, 사용 허가·상태·한도 검사 | 동일 | 동일 |
| Agent 설정/중지·재개 | 불가 | 현재 조직 운영 | 명시 관리 조직 운영. 공통 중지는 별도 platform 권한 |
| Job 상태/오류 조회 | 콘텐츠 ACL 있는 문서의 최소 상태 | 현재 조직 운영 최소 상태 | 명시 관리 조직 동일 |
| 실패 Job 재처리/공개 | 직접 재처리 불가 | 현재 조직 작업 권한 + 현재 문서/버전 권한 | 명시 관리 조직 동일 |
| usage 조회 | 본인의 현재 조직 사용량 | 조직 합계와 최소 호출 상태, 타인 prompt/답변 제외 | 명시 관리 조직 동일, 공통 합계는 별도 권한 |
| 한도/원장 변경 | 불가 | 상위 배정 이하의 조직 한도만 설정 | 프로젝트 승인30,000원 안의 배정/중지. 인간의 원장 직접 삽입/수정 불가 |

개인 문서의 명시 허용은 read 권한이며 관리/공유/owner 이전 권한을 뜻하지 않는다. 초기 등록 정책 이후 ACL/owner/visibility 변경 기능을 MVP에서 제공하지 않아 관리자 자기 추가로 개인 본문 제한을 우회하는 경로를 막는다. 필요하면 삭제 후 적법한 새 등록으로 처리하며 기존 문서/과거 근거의 권한을 자동 승계하지 않는다. 문서 삭제/재등록의 구체 상태는D240-05에서 정한다.

등록 관리자는 제출한 파일을 이미 알고 있을 수 있다. 여기서 보호하는 것은 등록 이후 서비스가 권한 없이 그 본문을 재반환하거나 검색에 사용하지 않는 조건이다. 개인 색인 Job의 내부 읽기는 human read 예외가 아닌, 특정 문서/버전·행동에만 묶인 위임 작업 권한이다. 운영 응답에는 본문/청크/프롬프트/민감 제목을 포함하지 않는다.

관리용 최소 Job 필드는 job_id·문서의 불투명ID·버전 식별·단계/상태·시각·정제된 오류코드다. usage는 호출ID·수행 주체 불투명ID·조직·모델 기본명·토큰/추정비용·상태/시각까지만 운영 필요에 따라 노출한다. 내부 원장 join으로 타인 질문을 가져오는 별도 경로를 제공하지 않는다. 실제 필드는D240-03/04가 구체화한다.

공유 D-S는 소유 조직 A를 유지한다. B는G-S-v1-B가 허용한 v1만 읽으며 v2가 발행되었다고 Grant를 자동 확대하지 않는다. A의 private 자료는 cross-tenant Grant를 만들 수 없다. 검색 실패/거부 시 숨겨진 제목/원 소유 조직/본문을 오류에 포함하지 않는다.

| 변경 주체/요청 | 판정 |
|---|---|
| USER의 소속 활성/역할 변경 요청 | 거부 |
| TADMIN의 같은 조직 USER 소속 활성/비활성 | 허용. 대상이 현재 USER이고 해당 조직에 속해야 함 |
| TADMIN의 TADMIN/PADMIN 대상 관리·승격/회수 | 거부. 일반 소속 상태 변경으로 관리자 회수를 우회하지 않음 |
| 관리 소속 있는 PADMIN의 다른 사용자의 USER↔TADMIN | 허용. 현재 조직에 한정, 대상이 PADMIN이면 UI 변경 금지 |
| PADMIN의 자기 역할/관리 범위/플랫폼 권한 변경 | 거부 |
| 어느 역할의 UI PADMIN 부여·전역 계정 상태/비밀번호 변경 | 이번 UI 범위 밖, 직접 API도 거부 |
| A 소속 비활성화 | A 신규 요청 거부. 활성 B 소속·전역 계정은 그대로 |

대상 membership의 변경 전 상태도 검사한다. 요청 body의 원하는 역할만 검사하면 TADMIN이 소속 비활성으로 다른 관리자를 제거할 수 있으므로 이를 금지한다. 현재 주체/대상 권한 재검사, 변경 저장, revision 증가와 감사 기록을 같은 성공 경계로 묶는다. 조직 변경 실패면 기존 역할/소속을 보존한다. 경합/잠금은D240-02가 구체화한다.

플랫폼 초기 권한·관리 소속 부여는 합성 초기화/운영 절차에서만 수행한다. P-A는 A 관리 소속과 공통 운영 권한을 가지지만 B 관리 권한은 없다. DUAL/DUAL-ADM은 A/B membership을 별도로 가진다. 초기 데이터의 액터ID는 선언이며 실제 계정/비밀번호/세션을 만들지 않았다.

## 7. 회수·진행 작업·경합

| 변경 | 이후 판정 |
|---|---|
| session 회수/만료 | 이후 HTTP 요청 인증 거부, 캐시/이력 응답 재사용 금지 |
| account 비활성/auth_revision 변경 | 이전 세션 및 위임 작업의 이후 승인 거부 |
| membership 비활성/role 회수 | 해당 조직 새 요청/관리 변경/새 provider 호출/Job 재시도·공개에서 현재 권한 검사 |
| Grant 회수/문서 삭제/버전 비공개 | 새 검색 후보/문맥 조립/근거·원문 조회 및 결과 공개에서 제외 |
| Agent 중지/한도 초과 | 신규 생성/임베딩·재시도 허가 거부. 이미 발생한 usage 보존 |

Job에는 initiator_user_id·tenant_id·문서/버전ID·허용한 행동·관련 revision을 기록한다. 실행/재시도·provider 호출 직전·공개 직전에 현재 계정/소속/운영 권한과 자원 유효성을 재검사한다. 일반 Job principal이 무제한 관리자 권한으로 모든 파일을 읽지 않는다. 개인 문서 등록/색인에 승인된 특정 버전의 internal_index 행동을 허용하되 해당 작업의 tenant/문서/버전을 늘릴 수 없다. 결과/상태를 사람에게 반환할 때는 별도로 현재 사람의 콘텐츠/운영 ACL을 적용한다.

권한 snapshot은 감사/변경 감지에만 쓰며 현재 승인 대체물이 아니다. 요청 간 허용 판정 캐시는 MVP에서 사용하지 않는다. 파일/Graph/벡터 캐시를 사용하게 되더라도 내용 반환 전에 현재 ACL을 검사하며 tenant/version/owner 없는 전역 key는 사용하지 않는다.

권한 회수 완료의 기준은 변경 트랜잭션의 commit이다. 그 이후 시작한 요청/중요 단계는 최신 상태를 읽고 거부한다. 변경과 업무 변경/공개가 동시에 발생하면 짧은 트랜잭션의 관련 권한 revision 검증/잠금으로 순서를 정한다. DB 잠금을 모델 네트워크 응답 동안 유지하지 않는다. D240-02가 구체 잠금·최신 조회/분리수준을 정하고D240-03/04가 호출/스트림/취소의 경합을 정한다.

권한 검사 후 이미 제공자에게 전달된 입력이나 사용자에게 전송된 답변을 회수했다고 주장하지 않는다. 회수 이후의 다음 provider 호출·결과 공개에는 다시 허가가 필요하다. 진행 스트림의 세션/권한 회수 감지와 중단 확인 간격은D240-03의 전송 계약에 연결한다. 과거 링크/미리보기는 현재 ACL로 차단하고, **저장 답변의 인용 본문 재표시 정책**은D240-05에서 버전/Grant와 함께 확정한다. D240-01만으로 해당 정책을 완료 처리하지 않는다.

## 8. 오류·감사와 모듈 책임

인증 실패/만료, tenant 형식 오류, 소속 없음, 자원 무권한, 정책 중지/한도는 내부적으로 구분한다. 외부 자원 오류는 다른 조직 자원의 존재·제목·파일 경로·내용을 노출하지 않는 일관된 응답으로 처리한다. 정확한 HTTP/오류코드는D240-03에서 확정한다. 브라우저 메뉴 숨김/role 표시·CSRF·UUID 비추측성이 자원 ACL을 대신하지 않는다.

| 책임 | 입력 | 출력·제약 |
|---|---|---|
| 인증/세션 | cookie·login 입력·현재 계정 | 인증 주체/내부 session, 비밀번호/쿠키 원문 반환 금지 |
| tenant resolver | 인증 주체·선택 tenant | 검증된 현재 membership/role 문맥. 누락 기본 거부 |
| authorization policy | 문맥·action·조회된 자원/버전/Grant | 명시 허용 또는 거부. 관리자 개인 본문 예외 없음 |
| tenant 저장소/RLS | 검증 문맥·자원 참조 | 허용 행/필드, runtime 비우회·트랜잭션 문맥 |
| Job worker | 저장한 제한 작업 참조 + 현재 권한 | 특정 작업 실행/공개 판정, HTTP 세션 복제/전역 mutable 문맥 없음 |
| UI | 허용 조직/자원·응답 상태 | 현재 탭의 표시/전환, 서버 검사 생략 불가 |

활동 기록은request_id·내부 actor ID·선택 tenant·action·대상 불투명ID·결과/정제된 사유·시각·관련 revision을 남긴다. 로그인 실패는 입력 계정의 존재 여부를 사용자에게 내보내지 않고 식별자 보관도 최소화한다. 비밀번호·session 원문·CSRF·API 키·개인 질문/답변·파일 본문/민감 제목은 기록하지 않는다. DB 제약/지속 저장과 실패 처리의 구체 계약은D240-02/03에 전달한다.

## 13. D240-08 통합 결과 — 종합 사용자 검토 대기

이 절과 갱신한4.3절을 현재 통합 계약으로 사용한다. 선행 작성/후속 계획은 당시 이력이다. [[200.프로젝트실행/240.설계/09 설계 검토 결과와 구현 전달]]에 변경/검토 대상·첫250 입력을 묶었다. 앱 구현/시험은 미수행이다.

DB membership.role은 USER/TADMIN만 저장한다. 합성 ACT-PADMIN은 USER membership + 활성 platform_access.is_padmin/permissions + 해당 managed_tenants로 매핑한다. 표시 effective_role=PADMIN은 그 조직의 관리 소속이 있을 때만 계산한다. 글로벌 permission은 조직 표시 역할과 독립이고 임의 다른 조직/개인 본문 권한을 부여하지 않는다. UI에서 PADMIN/자기 플랫폼권한을 부여/회수하지 않는다.

현재 세션/소속/자원 ACL은 매 조회/변경에서 검사한다. origin_session_id는 진행 run의 신규 단계/공개 gate이며, 적법한 새 세션으로 본인의 과거 완료 기록을 읽을 때 오래된 origin session을 복원할 필요는 없다. Agent/공통 중지는 신규/후속 호출과 진행 결과 공개의 통제이고 이미 적법하게 저장된 과거 답변을 일괄 삭제하는 권한 회수가 아니다. 과거 RAG 답변은 별도로 현재 모든 출처 권한을 검사한다.
