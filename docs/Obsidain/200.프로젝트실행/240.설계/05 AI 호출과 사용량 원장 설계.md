# AI 호출과 사용량 원장 설계

> **현재 기준 — 2026-10-04 종합 승인:** 사용자가 종합 설계 보고 후 “네 진행 바랍니다”로 후속 진행을 지시하여 이 설계를 확정했다. [[200.프로젝트실행/250.구현/01 인증과 테넌트 기반 구현 계획]]으로 전달한다. 아래 각 D240 작업 당시의 검토 대기/미수행 서술은 작성 이력이다. 현재250의A01~06 실제인증·조직관리·RLS·화면과재시작/실DB장애·복구·통합검증완료다. 첫기능A만완료이며다음B01/전체AI·Graph는후속이다. 최신결과는250.02의24~27절/B계획은250.03을따른다.

## 1. 결론·작성 상태·입력

일반/RAG 답변 생성과 문서/질의 임베딩은 **현재 권한 검사 → 중지·한도 검사 → 비용·동시 슬롯 예약 → 발사 기록 → 제공자 호출 → 사용량 기록**의 한 경로를 사용한다. 사용량 불명은 예약을 유지한다. 취소·권한 회수·결과 저장 실패로 이미 발생한 사용량을 지우지 않으며, 제공자 자동 재호출은 하지 않는다.

D240-04 문서 작성/자체 점검 완료. 사용자 “네 진행 바랍니다”를 D240-03 결과에 이은 순차 설계 진행 지시로 반영했다. 240 전체 설계 승인과 250 코드 착수 승인은 아직이다. 이 문서는 같은 FastAPI의 공통 AI 통제 계약이며 별도 API/AI Gateway 제품·서버를 만들지 않는다. 앱 코드·DB/계정/키 설정·모의/실제 API 시험·유료 호출은 수행하지 않았다.

입력: [[200.프로젝트실행/240.설계/02 인증과 테넌트 권한 설계]], [[200.프로젝트실행/240.설계/03 데이터 모델과 RLS 설계]], [[200.프로젝트실행/240.설계/04 API와 실행 상태 설계]], [[200.프로젝트실행/220.요구정의/05 공통 기능과 비기능 요구사항]], [[200.프로젝트실행/220.요구정의/06 요구사항과 검증 추적표]], [[200.프로젝트실행/230.분석/03 GraphRAG와 백엔드 재사용 분석]]. 문서 연결은 자체 점검에서 실제 파일과 대조했다.

| 통제안 | 부담·판단 | 선택 |
|---|---|---|
| 각 기능에서 직접 SDK 사용 | 간단한 초기 연결이 가능하나 권한/원장/중지 누락 경로가 생김 | 제외 |
| 같은 서버의 중앙 호출 서비스 + 제공자 어댑터 | 생성/임베딩의 허가와 기록을 한곳에서 검사 | **채택 설계안** |
| 별도 Gateway 서버/제품 | 추가 운영·설정·비용 | 이번 개인 MVP 범위에서 제외 |

## 2. 모델·작업·공통 인터페이스

생성은 `gpt-4o-mini`, 임베딩은 `text-embedding-3-small`, 임베딩 차원은1536으로 고정한다. 비용 최소화 지시를 유지한다. 모델 비교, 도구 호출/웹 검색, 자동 고가 모델 전환, 추가 Agent 유형을 넣지 않는다. Graph 관계 추출은 원문 기반 규칙으로 시작하며 추가 LLM 추출 호출을 넣지 않는다. D240-05에서 규칙·스키마와 한계를 정한다.

| operation | 대상과 허가 | SDK에 전달할 최소 입력 | 논리 단계 키 |
|---|---|---|---|
| generate_general | 본인 general run·현재 origin session | 서버 구성 지침/허용된 본인 이력/질문 | run + operation + generation |
| generate_rag | 본인 rules_rag run·현재 origin session·선택 근거의 현재 ACL | 같은 입력 + 허용된 근거 문맥 | run + operation + generation |
| embed_query | 본인 rules_rag run·검색 대상 ACL | 현재 질문1개 | run + operation + query |
| embed_document | 특정 Job·현재 initiator 권한·문서 버전/색인·lease | 해당 버전의 허용된 청크 묶음 | job + operation + batch ordinal/hash |

허가받은 공유 A 문서를 B 사용자가 검색하면 **질의/생성 비용은 실행 조직 B**에 기록한다. A 문서 색인 비용은 소유 조직 A의 Job에 기록한다. 문서의 소유 tenant를 검색자 B로 바꾸지 않는다.

중앙 서비스 입력 계약은 verified actor/tenant, run 또는 Job ID, execution/lease epoch, operation, 서버 결정 step_key, Agent 설정 revision, server mode, 입력과 입력 fingerprint, 토큰 상한이다. 브라우저가 model/key/provider URL/비용/usage/call ID/step_key를 지정하지 못한다. 일반 웹/GraphRAG/색인 코드는 중앙 서비스만 호출한다. GraphRAG 기존 직접 SDK 생성/임베딩 부분을 제공자 인터페이스로 바꾸는 구현 입력이다.

제공자 어댑터는 유효한 dispatch claim을 중앙 서비스로부터 받은 경우에만 실행한다. 출력은 draft delta, completion/embedding 결과, terminal observation, 정제된 usage receipt 또는 usage_unknown, provider request ID, 정제된 오류 분류다. 권한/예산/DB 쓰기와 최종 사용자 공개는 어댑터 책임이 아니다. receipt는 call/dispatch claim에 서버가 연결하며 사용자 입력 receipt는 수락하지 않는다. 완성 본문/벡터는 권한 있는 실행 경로로만 전달하고 meter에는 토큰/ID 등 최소 정보만 전달한다.

## 3. 입력·시간·제공자 응답 계약

| 항목 | 고정 설계값·거부 |
|---|---|
| 생성 입력/출력 | 최종 입력 최대6000토큰, 출력 최대1024토큰, 후보1개. 질문/필수 지침은 임의 잘라내지 않음 |
| 이력/RAG 문맥 | 최근 완전 메시지 최대6개를 입력 상한 내 선택. RAG는 기본입력4000 + 검색 문맥 최대2000. 전체 직렬화된 입력을 다시 검사 |
| 질의 임베딩 | 질문1개, 모델 tokenizer 기준 최대4000토큰, 공백 입력 거부 |
| 문서 임베딩 | 청크1개 최대512토큰, 한 API 요청 최대8청크/4096토큰. 공백 청크 제외. 청킹/겹침/문서 총 청크 상한은 D240-05에서 확정 |
| 요청 단위 | 생성 Chat Completions streaming, 임베딩 Embeddings 비스트리밍 응답을 비동기 어댑터로 대기. Batch API/제공자 파일 업로드 없음 |
| 제공자 전체 대기 | 생성60초/임베딩30초. 연결/읽기 timeout 외 별도의 전체 호출 deadline으로 제한 |
| 업무 전체 대기 | run180초/Job300초. 다음 단계 전에 잔여 시간을 검사. 상한 파일의 색인이 반드시300초 내 끝난다고 보장하지 않음 |
| 재호출 | SDK `max_retries=0` 및 별도 retry wrapper 없음. 429/5xx/timeout/빈 응답/JSON 오류도 자동 재호출0 |
| 실제 구동 | 한 FastAPI 프로세스/workers1. 유료 실행 중 자동 reload 없음. run/Job lease60초·heartbeat20초·epoch fencing은04 계약 유지 |

생성 요청은 model·messages·stream=true·stream_options.include_usage=true·max_completion_tokens=1024·n=1·service_tier=default·store=false를 서버가 결정한다. 출력 상한 필드(`max_completion_tokens`)의 실제 SDK/모델 호환은250에서 설치 버전과 공식 Create 문서를 다시 확인하고 대표 실제 호출로 검증한다. 이는 임의 fallback/상한 누락을 허용하는 뜻이 아니다. 호환 미확인이면 실제 모드를 기동하지 않는다. 텍스트만 전송하며 원장/로그에는 messages를 남기지 않는다.

Chat Completions의 마지막 usage chunk는 choices가 비어 있을 수 있고, 끊김/취소 시 해당 chunk를 못 받을 수 있다. 따라서 delta 수나 화면 글자 수로 확정 usage를 만들지 않는다. 어댑터는 빈 choices와 usage chunk를 별도로 처리한다. [공식 Chat 스트림 계약](https://developers.openai.com/api/reference/resources/chat).

완전한 텍스트와 정상 finish_reason=stop을 확인한 경우에만 정상 생성 결과 후보로 본다. length는 `OUTPUT_TRUNCATED`, content filter/refusal은 `RESPONSE_BLOCKED`, 빈 본문은 `EMPTY_RESPONSE`로 최종 정상 답변을 만들지 않는다. 해당 호출의 usage가 있으면 실패 답변이어도 기록한다. 정상 완료 신호 전의 EOF/timeout은 미완성이다. RAG 근거 부족은 검색 오류와 구분하며 일반 답변으로 자동 전환하지 않는다. 정상 무근거 판정은 로컬 안내로 completed+insufficient_evidence를 만들 수 있고, 이미 수행한 질의 임베딩 비용은 남긴다.

임베딩은 model·encoding_format=float·dimensions=1536을 서버 고정값으로 전달한다. 입력별 response index가 정확히1개씩 있고, 길이가1536이며 모든 값이 유한한지 검사한다. 누락/중복/index mismatch/NaN/차원 오류는 `INVALID_EMBEDDING_RESPONSE`다. 실제 모드에서 가짜 벡터/0벡터/다른 모델로 대체하지 않는다. 잘못된 벡터여도 받은 usage는 기록한다. 기본1536차원과 임베딩 토큰 계산 기준은 [공식 임베딩 안내](https://developers.openai.com/api/docs/guides/embeddings)를 확인했다.

usage receipt는 서버가 관측한 해당 call의 응답만 수락한다. 입력/출력/total 토큰은 비음수 정수이며 생성의 total=input+output, 임베딩의 total=input을 확인한다. 필수 usage가 빠지거나 숫자/합계가 맞지 않으면 확정 정산하지 않고 unknown으로 보존한다. 캐시 세부값이 없어도 전체 input을 표준 단가로 추정하며 할인 확인을 정산의 필요조건으로 삼지 않는다. request model과 response model을 구분해 저장한다. 생성 응답은 선택 alias 또는 공식 확인된 gpt-4o-mini-2024-07-18 snapshot, 임베딩은 선택 모델을 허용한다. 예상 밖 모델/tier는 정상 결과를 공개하지 않고 MODEL_POLICY_MISMATCH로 real 신규 호출을 중지한다. 관측 토큰은 보존하되 미확인 모델 단가를 기존 단가로 확정하지 않고 비용 예약을 유지한다. 이는 자동 모델 변경 경로가 아니다.

입력 토큰은 해당 모델용 tokenizer와 메시지 직렬화 여유를 포함해 검사한다. 질문 문자 제한은04의4000자/JSON 크기 제한과 함께 적용한다. tokenizer/설정이 준비되지 않으면 실패하며 문자 수만으로 유료 허가하지 않는다. 생성은 항상6000입력+1024출력 상한으로 예약해 API usage와 로컬 계산 차이의 여유를 둔다. 실제 상한 적합성은 대표 시험에서 확인한다.

## 4. 허가·예약·발사·기록 순서

| 단계 | 현재 검사와 지속 저장 | 외부 호출 허용 |
|---|---|---|
| A. 접수/claim | 04의 client_send_id/operation receipt로 같은 실행을 확인. running claim과 epoch를 가진 단일 실행자만 다음 단계 가능 | 불가 |
| B. 입력/현재 권한 | 활성 계정/소속, 실행 tenant, 본인 run/origin session 또는 특정 Job/현재 initiator 권한·lease, 현재 Agent/문서·Grant ACL을 검사. 서버 config/mode 및 입력 상한 검사 | 불가 |
| C. 원자 예약 | authority→Agent→project budget→tenant budget→run/Job/call 순의03 잠금. 최신 중지/한도·기간·slot을 검사. call+reserve event+금액/slot 집계를 같은 transaction에 commit | 불가 |
| D. 발사 claim | 예약 유효기간10초 내 같은 잠금 순서로 현재 권한/중지/예산/config revision/epoch 재검사. reserved→dispatched CAS와 dispatch timestamp/claim을 commit. 응답 유실이면 DB를 확인하되 dispatched call을 다시 발사하지 않음 | CAS 성공을 확인한 원 실행자에게1회만 허용 |
| E. 제공자 대기 | DB 잠금/transaction을 닫은 뒤 어댑터1회 호출. provider request ID/usage/종결 관측은 정제 기록. heartbeat와 현재 공개 검사 분리 | 추가 발사 불가 |
| F. 사용량/결과 | meter가 저장 call/permit으로 usage 정산. 콘텐츠 저장/공개는 현재 사람/문서/Agent 권한과 실행 CAS로 별도 검사. 최종 완료는04의 DB commit 뒤 | 재호출 불가 |

C 또는 D가 실패하면 provider0이다. 예약과 외부 HTTP를 하나의 atomic transaction이라고 주장하지 않는다. D commit 직후 중지/회수 또는 프로세스 장애가 생기면 실제 제공자 도달 여부가 불명일 수 있다. 이 경우 예약을 유지한다. dispatch 이후 best effort 중단은 제공자의 무과금/처리 취소 확인과 같지 않다.

C에서 얻은 설정 revision과 dispatch 직전 설정이 다르면 미발사 예약을 해제하고 해당 실행을 blocked로 종결한다. 조용히 새 지침/모델로 계속하지 않는다. 사용자는 현재 설정으로 새 실행을 시작할 수 있다. Job의 상태/재처리는04/06의 기준을 따른다.

C와 D 모두 기존 현재 검사/짧은 잠금으로 선후 관계를 정한다. 공유 공개/Grant 부재 경합도03의 publication 잠금을 사용한다. SDK 입력에 포함될 문서 근거를 permission fingerprint에 묶으며 발사 직전 해당 출처들의 현재 ACL을 재검사한다. 잠금으로 네트워크 도중 권한을 고정하지 않는다. 이후 회수 시 새로운 본문 전달/최종 공개는 차단하고 비용 기록만 계속한다.

예약 유효기간10초는 금액을 자동 해제하는 TTL이 아니다. 시스템 복구가 reserved 상태 및 dispatch 미발생을 DB에서 확인한 경우에만 해제한다. dispatched 기록의 수명 경과는 미발사를 증명하지 않는다.

## 5. 원장·call 상태·중복 판정

03의 ops.call_attempts/usage_events/project_budget/tenant_budgets를 사용한다. 테이블을 실제 생성하지 않는다. 금액 numeric(18,6), counter 비음수, event append-only, `(tenant,call,event_kind)` UNIQUE를 유지한다.

| call state | 의미 | 금액 예약 | 슬롯 |
|---|---|---|---|
| reserved | 비용/slot 예약 commit, 아직 dispatch 없음 | 유지 | 점유 |
| dispatched | 단일 dispatch claim commit, 실제 HTTP 도달 여부까지 확정하는 상태 아님 | 유지 | 점유 |
| usage_unknown | dispatch 이후 확정 usage 증거 없음/정산 저장 불명 | 유지 | 제공자 종결 증거 없으면 격리 점유 |
| settled | 신뢰할 수 있는 provider usage를1회 기록 | 해제하고 같은 snapshot의 비용 추정으로 accounted 증가 | 제공자 종결 증거 있으면 해제 |
| released_no_dispatch | DB상 미발사 확인 후 해제 | 해제·accounted 증가0 | 해제 |

별도 `provider_end_status=not_started/observed/unknown`과 `slot_held`를 둔다. usage 확인과 원격 실행 종료는 별개다. 전체 정상 HTTP 응답 또는 모든 후보의 종료를 확인한 스트림 종결 증거로 slot을 해제할 수 있다. usage만 받았지만 정상 종결 관측이 없는 예외는 slot을 유지한다. 네트워크 timeout/abort만으로 remote 종료를 observed로 바꾸지 않는다. 정상 finish를 확인한 답변에서 마지막 usage가 유실되면 **금액 예약은 유지하되 종료 증거가 있는 slot은 해제**할 수 있다.

| event_kind | 발생 조건·한 번의 변화 |
|---|---|
| reserve | 새 call 예약: reserved +R, accounted +0 |
| mark_unknown | dispatched에서 usage 미확인: 금액 변화0, 증거/원인 최소 기록 |
| settle | dispatched/usage_unknown에서 확정 usage: reserved −R, accounted +C. 동일 call에 최종1회 |
| release | reserved에서 미발사 확인: reserved −R, accounted +0. settle과 상호배타 |

slot 해제는 같은 call의 `slot_held=true→false` CAS 및 project/tenant 집계를 같은 transaction으로 변경하고 중복 해제하지 않는다. event UNIQUE만으로 settle/release 상호배타를 보장할 수 없으므로 call state CAS도 필수다. 동일 종류 receipt를 다시 받으면 no-op; 다른 토큰/증거가 들어오면 `LEDGER_CONFLICT`로 신규 호출을 중지하고 대조 대상으로 남긴다. 관리자가 원장 행을 직접 수정/삭제하는 API는 없다.

logical step_key UNIQUE는 `(tenant,run,operation,step_key)` 또는 `(tenant,job,operation,step_key)` 부분 고유키로 추가한다. operation별 attempt_no는 기존 필드로 남기되 별도의 SDK 재시도 횟수로 해석하지 않는다. 같은 run의 query/generation은 각각 최대1 call, Job 배치 ordinal은 서버 계획에 고정한다. 동일 step의 동시 호출은 기존 call을 조회한다. **기존 reserved/dispatched를 찾았다는 이유로 두 번째 호출자가 SDK를 발사하지 않는다.** 실행 epoch와 dispatch claim을 함께 확인한다.

유료 재시도는 기존 call을 덮어쓰지 않는다. 채팅은 사용자 명시 새 client_send_id의 새 실행이며 현재 권한/한도를 다시 검사한다. Job은04의 새 retry Job/receipt와06의 재사용 가능 단계 검사를 거친다. usage 불명 Job은 needs_review이며 자동/수동 재처리 API로 우회하지 못한다. 확정 실패인 배치도 기존 지출은 유지하며 새 비용을 다시 예약한다.

## 6. 단순 비용 기준·상한·대조

2026-10-04 공식 모델 문서의 표준 텍스트 단가: 생성 입력 $0.15/출력 $0.60 per1M tokens, 임베딩 입력 $0.02 per1M tokens. 캐시/Batch 할인은 예약에 반영하지 않는다. [gpt-4o-mini 단가](https://developers.openai.com/api/docs/models/gpt-4o-mini), [text-embedding-3-small 단가](https://developers.openai.com/api/docs/models/text-embedding-3-small).

PADMIN도 승인30,000을 확대하지 못한다. 실제 초기 A/B 배정값은250의 합성 초기화 계획에서 상위합계 안으로 정하며 지금 운영 DB 값을 만들지 않는다.

이미 발생한 C가 R/운영상한을 넘더라도 정산 저장을 거부하지 않는다. 예약 해제+accounted 증가를 기록하고 `cost_overrun`/프로젝트 중지 latch를 남긴다. cap 이하 CHECK로 기발생 지출을 숨기지 않는다. counter 합계와 event 대조가 맞지 않으면 신규 허가를 차단한다. 실제 범위는2026-10월이며11월1일00:00 Asia/Seoul 이후 신규 real call은 승인된 다음 기간 예산이 없으면 거부한다. UTC 저장값과 기간 판정 시간대를 혼동하지 않는다.

대표 실제 호출 전과 실제 시험일의 첫 유료 실행 전에 공식 모델/API/단가 및 계정 프로젝트 사용량을 대조한다. 단가 변화는 서버 설정 version 변경·재검토 대상이며 실시간 가격 UI를 만들지 않는다. 이 플랫폼용 전용 OpenAI 프로젝트/서버 키를 준비해 외부 사용 혼입을 줄인다. 대조는 별도 Admin API 자동수집 없이 계정 화면의 프로젝트 기간 사용량으로 시작한다. 계정 집계가 특정 call의 미실행/무과금을 증명한다고 보지 않는다. call별 증거가 없으면 unknown 예약을 유지한다. 원화 실제 청구 확인은 별도 운영 대조이며 차이가 크면 real 신규 호출을 중지한다. 앱 밖 동일 계정 사용/환율 변동까지 자체 예약만으로 강제 통제했다고 주장하지 않는다.

## 7. 중지·설정 변경·동시 슬롯

Agent 설정은 tenant+general/rules_rag의 revision과 immutable 실행 snapshot으로 기록한다. 키/모델/provider URL은 관리자 Agent 설정 필드가 아니다. stop은 프로젝트 공통·조직 한도/운영·해당 tenant Agent enable을 합쳐 판정한다. 문서 임베딩도 해당 조직 rules_rag 중지 gate를 거친다. general 중지만으로 다른 조직이나 rules_rag를 변경하지 않는다.

| 변경 시점/대상 | 처리 |
|---|---|
| 예약 전 중지/부족/회수 | 예약/dispatch/provider0, 정제된 blocked/오류 기록 |
| reserved 상태의 중지/권한 회수/config 변경/기간 만료 | D 재검사에서 거부, 미발사 확인 후 release, 신규/다음 단계 없음 |
| dispatched 이후 중지/취소/권한 회수 | best effort SDK 중단, 새 단계/본문 공개 차단, 기존 usage 기록. 불명 비용/slot 보존 |
| Agent 지침만 변경, 이미 발사됨 | 해당 call snapshot은 바꾸지 않음. 다음 단계의 revision mismatch는 차단. 이미 발사된 결과 공개는 현재 enable/권한과04 CAS로 검사 |
| local cap/배정 축소 | 이미 발생한 비용/예약은 유지. 사용+예약이 새 cap 초과면 미발사 단계 차단. 기발사 정산을 누락하지 않음 |
| 중지 해제 | 현재 권한/배정/기간/config/미확인slot/counter를 검사. 과거 blocked/cancelled/interrupted run/Job을 자동 재개하지 않음 |

project provider 슬롯2개, tenant1개를 생성/질의·문서 임베딩이 공동 사용한다.04의 run/Job 접수 동시 수와 별개다. 한 RAG run은 query 정산/종료 뒤에 generation 슬롯을 새로 얻는다. SDK 호출을 동시에 중첩하지 않는다. slot은 budget 행 잠금과 call slot_held 집계로 원자 예약한다. 실제 runtime semaphore만으로 재시작/다른 DB 연결의 제한을 대체하지 않는다.

slot 대기는 DB transaction 밖에서 최대5초, 기다리는 동안 새 reservation 없음, 다시 현재 권한을 검사한다. 끝까지 불가하면 `EXECUTION_CAPACITY_EXCEEDED`다. 접수 전 HTTP는04의429/Retry-After, 이미 접수된 run/Job는 조회 HTTP200 안에 blocked/정제 오류를 기록한다. quota는 `QUOTA_EXCEEDED`, 미확인 격리 슬롯이 원인이면 `REVIEW_REQUIRED`를 표시한다. UI가 새 전송으로 무한 재시도하지 않는다.

원격 종결 증거가 없는 usage_unknown call은 격리 slot을 유지한다. 경과 시간/로컬 task 종료/재시작/관리자 재개 버튼으로 해제하지 않는다. 최대2개가 격리되면 real 신규 호출이 멈출 수 있으며 확인 전 자동 복구를 약속하지 않는다. 그 사이 mock 검증은 real과 분리해서 수행 가능하다. 특정 call에 연결된 신뢰할 수 있는 종결/usage 증거를 확보한 경우만 시스템 제한 정산 함수로 복구한다. provider request ID만으로 임의 결과 조회/정산이 가능하다고 가정하지 않는다.

settle/release/mark_unknown은 meter runtime의 저장 permit/현재 call state/서버 receipt를 검사한다. 사람의 현재 세션/역할 활성 검사는 **기발생 정산**의 필요조건이 아니다. 이 예외로 새 provider call/콘텐츠 조회/Job 공개는 허용하지 않는다. 오래된 실행자의 콘텐츠 쓰기는 epoch로 차단하되 그 실행자가 발사한 call의 정당한 usage receipt는 비용 기록만 수락한다.

질의 임베딩 이후 검색 실패, 근거 문맥 후6000토큰 초과, 생성 중지/한도 거부에서는 generation0이지만 embed_query 사용량은 유지한다. 회수·삭제는 진행 call과 파생 공개를 차단하는 정책이며 비용 제거 기능이 아니다. 같은 send ID/재연결/조회 subscriber는 기존 call에 접근할 뿐 새 유료 호출을 만들지 않는다.

## 9. 실제/모의·키·최소 노출

서버 기동 mode=mock 또는 real을 명시한다. 기본은 mock이다. real에서 키/지원 모델/입력 상한/현재 공식 API 확인이 미완료면 설정 오류로 실행을 거부한다. real 실패를 mock 성공으로 자동 대체하지 않는다. mode는 사용자가 API마다 고르는 옵션이 아니다. 실행/Job/call/budget/usage에 mode를 고정하고 미종결 call이 있는 mode 전환은 별도 운영 정리 후 서버 재기동으로 수행한다.

mock도 같은 ACL/예약/중복/중지/정산 경로와 실제 PostgreSQL 계약을 검증한다. 제공자 응답만 재현 가능하게 주입한다. **mock 원장과 real 원장을 별도 budget_id/period+mode로 구분**하고 real 합산 지출에서 mock 비용을 제외한다. mock용 소액 잔여액/오류 fixture는 시험 전용 값이며 real 승인cap을 변경하지 않는다. 실제 구현 전 DB/fixture 생성은 없다.

키는 서버 환경/비추적 설정 또는 운영 비밀 저장소만 사용한다. 브라우저·Obsidian/Git·Agent 설정·URL·응답·로그·합성 문서에 넣지 않는다. 서버 어댑터만 키를 읽고 GraphRAG/frontend/index 업무에는 키 객체나 직접 SDK 권한을 전달하지 않는다. 구현 검증에서 SDK import/클라이언트 생성·HTTP 요청·직접 provider 경로를 검색해 어댑터 밖 우회를 제거한다. 원본 코드를 지금 변경하지 않는다.

노출 허용 필드는 현재 권한 안의 operation/model/mode/run 또는 Job ID·call ID·토큰 확인 상태·비용 추정·예약 미확인액·안전 오류코드·시간이다. provider request ID는 보호 운영 기록으로만 남긴다. provider 원문 오류·키·headers·messages·문서 제목/본문·SQL·stack은 응답/ops 로그에 넣지 않는다. SDK/HTTP debug 원문 로깅도 사용하지 않는다. 개인 콘텐츠 권한과 사용량 관리 권한은02/03 그대로 구분한다.
