# 사용자와 관리자 화면 설계

## 1. 목적과 수행 상태

2026-10-04 사용자 “네 진행 바랍니다”에 따라 D240-06을 수행했다. 230의 화면 7묶음과 UP12/AP13을 인증·현재 권한·API·실행/Job·AI 원장·문서/GraphRAG 계약에 연결한 텍스트 화면 명세다. 문서 작성/자체 점검 완료이며 240 종합 사용자 승인, 화면 구현, 브라우저/API/DB/모델 시험 완료를 뜻하지 않는다. 예상20분은 기존215분 문서 계획 안의 배정값이며 실제 구현 공수/실제 작업 시간 측정값이 아니다.

React/Vite 사용자·관리자 포털, 공통 FastAPI, PostgreSQL, common_core GraphRAG 구조와 고정 Agent 2개를 유지한다. 별도 Home·Marketplace·자유 Canvas·GPU·구매형 Gateway·추가 관리자 제품·복잡한 과금 화면은 추가하지 않는다. 화면 7묶음은 주요 업무 구분이며 상태마다 정적 화면 7장만 만들겠다는 뜻은 아니다.

## 2. 화면 지도와 진입 권한

경로는 화면 책임을 설명하는 논리 경로다. 지금 라우터/컴포넌트/디자인 시스템을 생성하지 않는다. 로그인 뒤 API-03/05로 현재 세션·소속을 조회하고 본인에게 허용된 조직을 선택한다. 조직 누락 시 첫 조직으로 요청을 자동 전송하지 않는다. 허용 조직이 하나라면 그 조직명을 보여 주고 선택 상태를 명시한다.

| 묶음 | 논리 경로/메뉴 | 핵심 정보·행동 | 진입 권한 | 주요 API |
|---|---|---|---|---|
| UI-01 | /login · 로그인 | 계정/비밀번호, 실패/만료 안내, 로그인 | 미인증 진입; 인증 후 허용 조직 선택 | API-02~05 |
| UI-02 | /workspace · AI 업무 | 조직/Agent 선택, 질문, 답변, 내 대화, 근거/원문, 내 사용량 요약 | 현재 활성 조직 소속; 모든 역할도 본인 업무만 | API-06~17, API-35 |
| UI-03 | /admin/members · 사용자·역할 | 현재 조직의 기존 소속/활성/역할, 변경 결과 | TADMIN 또는 관리 소속 있는 PADMIN; 변경별 추가 제한 | API-18~20 |
| UI-04 | /admin/documents · 문서·색인 | 등록/버전, 실제 처리 상태, 삭제, 공유/회수 | 현재 조직 관리; 개인 본문은 별도 읽기 ACL | API-21~31 |
| UI-05 | /admin/agents · Agent 운영 | 고정2개 이름/설명/기본지시문, 저장, 중지/재개 | 현재 조직 관리 | API-32~34 |
| UI-06 | /admin/usage · 사용량·한도 | 조직 합계/호출 상태, 배정/조직 제한, 예약/확인 필요 | 현재 조직 관리; 상위 배정 변경은 해당 관리 소속 PADMIN | API-36~38, API-41 |
| UI-07 | /platform · 플랫폼 운영 | 프로젝트 합산, 공통 운영 상태/중지·재개 | 현재 PADMIN + 해당 플랫폼 권한 | API-03 보완필드, API-39~40 |

UI-02의 내 대화·근거·Agent 설명·내 사용량은 패널/영역으로 묶는다. 별도 사용자 Home이나 관리자용 ChatbotWidget을 사용자 업무의 주 화면으로 대체하지 않는다. 사용자 업무/관리 메뉴를 구분하되 동일 인증 기반을 사용한다. API-01 health는 운영 생존 확인용으로 화면 업무 데이터/합격 수치를 제공하지 않는다.

공통 헤더: **현재 조직명 / 현재 조직 역할 / 사용자 업무·허용 관리 메뉴 / 로그아웃**. 운영자에게 허용된 UI-07은 별도 진입으로 표시하며 들어가면 범위를 **프로젝트 전체**로 명시한다. 전체 사용량 화면에서 타 조직 본문·개인 문서·전체 계정 목록으로 내려가는 링크를 만들지 않는다. 조직 관리 화면은 헤더와 해당 요청의 조직이 항상 일치해야 한다.

메뉴 숨김은 편의를 위한 표시 제어다. 직접 경로/API 호출은 서버가 현재 세션·소속·권한·자원 ACL로 다시 검사한다. PADMIN이라는 명칭만으로 모든 조직 관리 메뉴/개인 자료/플랫폼 제어를 열지 않는다.

## 3. 조직·세션·화면 상태의 공통 계약

| 사건 | 화면 처리 | 요청/보호 조건 |
|---|---|---|
| 최초/새 탭 진입 | 현재 세션/소속 확인 전 업무 본문 표시 보류; 로딩/실패 구분 | API-03/05. 과거 localStorage의 조직을 권한으로 취급하지 않음 |
| A→B 조직 전환 | 질문 초안·대화/답변·근거·문서/원문·선택파일·관리 편집·목록·사용량·오류를 비움; B 권한/목록 새로 조회 | 선택 세대 번호 증가; 요청 생성 때 user/org/세대를 캡처; 늦은 A 응답/이벤트 폐기 |
| 탭2개가 A/B 사용 | 각 탭 선택/상태 독립. 전역 세션의 active tenant 변경으로 다른 탭을 덮어쓰지 않음 | 요청별 X-Tenant-ID; 캐시 키에 user/org/자원/현재 권한 문맥 포함 |
| 역할/소속/자료 권한 변경 | 새 응답에서 관리 메뉴/본문/근거 즉시 제거; 표시 가능 여부 재조회 | 메모리 캐시는 권한 판정 근거가 아님. 초점 복귀 시 세션/현재 자원을 재검사 |
| 세션 만료/로그아웃 | 민감 상태·열린 원문을 비우고 로그인 안내; 로그아웃 확인 후 다른 탭에도 상태 정리 알림 | HttpOnly 서버 세션. API-04 실패는 서버 로그아웃 완료로 표시하지 않음; 503이면 로컬 비움 + 재확인 안내 |
| 연결 끊김/탭 숨김 | 연결 안내; 숨긴 탭의 조회 반복 중단. 복귀 시 현재 snapshot 조회 | stream 종료/조직 전환/탭 닫기는 업무 취소가 아님. 실행 재호출하지 않음 |

질문/답변/원문/CSRF를 브라우저 영구 저장소에 저장하지 않는다. 민감 캐시는 메모리에만 두고 조직·주체·권한 변화 때 제거한다. 로그아웃 탭 알림을 구현하면 같은 출처 탭에 상태 변경 사실만 전달하고 본문/쿠키/CSRF는 전달하지 않는다. 이미 다운로드한 파일을 회수할 수 있다고 표시하지 않는다.

서버 세션 절대8시간/유휴30분은 02 계약을 따른다. 자동 상태 조회/연결 유지 신호로 유휴 만료를 연장하지 않는다. 자동 GET 재조회는 안전한 조회에 한해 최대2회(1초/3초); 유료 실행이나 관리 변경을 새 ID로 반복하지 않는다. 이력/관리 목록 기본20건·최대50건 및 서버 커서를 사용한다.

화면 문구는 “조직”, “자료 접근 권한”, “저장 확인 필요”처럼 업무 언어를 사용한다. lease/epoch/RLS/HTTP 상태/SDK 오류는 제품 문구로 노출하지 않는다. 오류 문의에는 비민감 요청 식별번호만 제공한다. 실패 응답에 있던 보호 제목·ID 존재·내부 경로·비밀키·원문을 보여 주지 않는다.

## 4. UI-01 로그인과 공통 오류 표시

계정/비밀번호 입력 → 제출 중 버튼 비활성 → API-02 성공 → API-03/05 현재 세션·소속 확인 → 조직 선택/UI-02. 비밀번호를 URL/기록/영구 저장소에 남기지 않는다. 실패·비활성 계정·잘못된 비밀번호는 “로그인 정보를 확인해 주세요.”로 묶고 계정 존재 여부를 구분하지 않는다. 계정 생성·초대·비밀번호 변경·SSO는 이번 화면/API 범위 밖이다.

| 응답/상황 | 제품 표시와 다음 행동 |
|---|---|
| 로그인/목록 조회 중 | “확인 중”; 사용자 데이터 임시 표시 금지 |
| 조직 소속 없음 | “사용 가능한 조직이 없습니다.”; 관리 권한 요청 안내만, 임의 조직 생성/선택 없음 |
| 400/413/415/422 | 해당 입력/파일 범위를 안전하게 안내; 서버 거부 결과를 표시 |
| 401 | 로그인 화면 이동/세션 만료 안내; 유료 전송 자동 반복 없음 |
| 403 | “현재 권한으로 수행할 수 없습니다.”; 조직/역할 현재값 재조회 후 무권한 영역 비움 |
| 404 | “자료를 찾을 수 없거나 접근 권한이 변경되었습니다.”; 보호 자료 존재/버전 구분 없음 |
| 409 | 설정 변경 충돌/운영 중지/한도/재처리 검토 필요를 서버의 안전한 분류로 안내 |
| 429 | “잠시 후 다시 시도해 주세요.”; 서버 대기 안내 반영; 새 호출 자동 반복 없음 |
| 500/503/통신 실패 | “처리 결과를 확인할 수 없습니다.” + 안전한 조회/문의. 실패와 저장 여부 불명을 구분 |

GET 성공 응답에 실행 failed/blocked가 들어오면 조회 성공과 업무 실패를 별개로 표시한다. GET 503만으로 이미 접수된 실행을 실패 종결 처리하지 않는다.

## 5. UI-02 사용자 업무 화면

화면 상단 조직·실제/모의 표시, 좌측 내 대화 목록, 중앙 고정 Agent 선택/설명·질문/답변, 우측 또는 하단 근거/원문 패널을 둔다. 작은 화면은 내 대화/근거를 접고 단일 업무 영역으로 전환하되 조직/역할/실행 상태는 계속 보인다. 실시간 업무/모의 데이터 표시는 서버가 반환한 모드로 결정하며 사용자가 표시만 바꾸는 토글을 두지 않는다.

### 5.1 질문·Agent·대화

- 일반 질의 `general`: “문서 검색 사용 안 함”. 문서 근거가 있는 듯한 표시/인용을 생성하지 않는다.
- 규정 질의 `rules_rag`: 현재 허용된 규정의 담당·기한·관계를 확인하는 제한된 업무. 전체 문서 자유 요약 기능으로 설명하지 않는다. Agent가 중지/한도 제한이면 설명과 안전한 사유를 표시하고 신규 전송을 막는다.
- 질문은 최대4,000문자 안내/카운터와 빈 입력 검사를 둔다. UTF-8 바이트/토큰/검색 후 문맥 제한은 서버가 검사한다. 전송 단축키는 Ctrl/Cmd+Enter로 두고 한글 조합 중 전송을 막는다. 단순 Enter는 줄바꿈이다.
- 선택 가능 자료는 API-17의 현재 허용 공개 버전만 사용한다. 지정 시 최대5개 참조; 목록이 비었다고 임의 문서/숨겨진 최신 버전을 추가하지 않는다.
- 전송 시작 시 client_send_id를 생성/보관하고 중복 버튼을 잠근다. 응답 불명은 API-11 조회 후 같은 ID 재전송 최대1회로 해결한다. 기존 실행 발견 시 그 실행으로 돌아간다. 새로운 ID 재전송/새 SDK 호출로 저장 불명을 해소하지 않는다.
- 내 대화는 API-07~09의 현재 조직/본인 결과만 표시한다. Agent 변경은 새 대화를 시작하고 초안을 비운다. 진행 중 실행은 시작한 Agent/config snapshot을 유지한다. 선택 변경으로 수락된 질문의 Agent를 덮어쓰지 않는다.
- “다시 질문”은 종결 상태와 현재 권한을 확인한 사용자의 명시적 새 행동으로 처리한다. 자동 실패 복구/유료 재시도 버튼과 혼동하지 않는다.

### 5.2 실행·본문·취소 상태

| 서버 상태/내용 | 사용자 표시 | 가능한 행동/완료 기준 |
|---|---|---|
| 전송 전/빈 이력 | “질문을 입력해 주세요.” / “아직 대화가 없습니다.” | 빈 상태는 조회 성공 후에만 표시 |
| accepted, stage queued | “접수됨 · 처리 대기” | 실행 ID 수신 후 이력/상태 조회; 취소 요청 가능 |
| running, authorization/retrieval | “자료와 접근 권한 확인 중” | 단순 시간 경과로 진행률/완료를 만들지 않음 |
| running, generation 일반 | “답변 작성 중 · 아직 저장되지 않음” | 허용된 임시 stream 표시, 확정 본문과 구분 |
| running, generation RAG | “근거 확인 중” | 원시 모델 JSON 숨김. 서버 검증한 사실/인용으로 구성한 임시 본문만 표시 가능 |
| running, finalizing | “저장 확인 중” | 끝난 stream만으로 완료/저장 성공 표시 금지 |
| completed + answer/final | “완료” | DB 저장 완료 응답 이후 확정 본문/이력 표시 |
| completed + insufficient_evidence | “허용된 자료에서 답을 확인할 수 없습니다.” | 질문 구체화/자료 상태 확인 안내; 일반 Agent 자동 전환/허위 근거 없음 |
| cancel_requested | “취소 요청됨 · 결과 확인 중” | API-13 접수는 종결 아님; 재요청 버튼 잠금/상태 조회 |
| cancelled | “취소됨” | 서버 종결 확인. 이미 발생한 사용량/예약은 별도 상태 |
| failed/blocked/interrupted | “처리 실패” / “현재 처리할 수 없음” / “처리가 중단됨” | 안전한 분류/요청 ID 표시. 임시 본문을 확정 저장 답변으로 표시하지 않음 |
| 통신/저장 결과 불명 | “연결 또는 저장 상태 확인 필요” | API-11/12로 현재 상태 확인. 새 실행/추가 과금 자동 발생 금지 |
| completed + content_status unavailable | “권한 또는 자료 상태가 변경되어 답변을 표시할 수 없습니다.” | 완료 시각/안전한 실행 상태 유지, 보호 본문·이전 임시 본문 비움 |

실행 상태와 `answer_kind/content_status/usage_status`는 서로 다른 축이다. 실행 completed라도 회수된 본문은 다시 보이지 않을 수 있으며 usage unknown을 성공/0원으로 바꾸지 않는다. 취소는 본인 실행 API-13의 명시적 행동만 사용한다. 완료 저장이 먼저 이기면 완료를 유지하고, 취소 종결이 먼저 이기면 이후 본문 저장을 막는 서버 CAS 결과를 따른다.

fetch SSE API-14는 조직 헤더/쿠키를 사용한다. 이벤트의 run/user/org/선택 세대를 확인하고 late event를 폐기한다. 재연결은 전체 snapshot 또는 API-12 조회를 사용하며 생성 API를 새로 호출하지 않는다. 2초 상태 조회는 화면이 보일 때만 사용한다. 250ms 표시 묶음·64KiB 이벤트 버퍼·15초 연결 유지 등 04의 값은 개발 계약이며 제품에서 가짜 백분율로 환산하지 않는다.

### 5.3 근거·원문·이력·내 사용량

API-15는 인용 순번/현재 허용 제목/정확 버전/위치/문장만 표시한다. API-16 원문 버튼은 누를 때 현재 권한을 다시 확인하고 정확한 인용 버전의 안전한 텍스트를 제공한다. 파일 경로/색인 내부 ID/비허용 최신 제목/조직 B에 없는 v2 사실은 보여 주지 않는다. revoked/삭제/버전 교체로 조회가 거부되면 열린 원문도 비운다.

저장된 RAG의 원천 하나라도 현재 허용되지 않으면 **저장 답변 본문 전체를 비운다**. 현재 허용된 근거 항목만 별도 패널에서 제공할 수 있고, 비허용 항목은 순번과 공통 접근 불가 안내만 표시한다. 일부 문장을 임의로 남기거나 다른 답변으로 다시 생성하지 않는다. 다음 질문의 서버 이력에서도 해당 보호 답변/연결된 턴을 제외하는 06 계약을 유지한다.

UI-02 내 사용량(API-35)은 본인/현재 조직/기간의 최소 요약이다. 조직 전체 잔액·다른 사용자 호출·질문 내용까지 제공하지 않는다. “확인된 토큰/추정 금액”, “예약 금액”, “사용량 확인 필요 · 예약 유지”를 구분하고 실제 공급자 청구서/실시간 환율로 표현하지 않는다.

## 6. UI-03 사용자·역할 관리

현재 관리 조직의 기존 membership을 계정 표시명/현재 역할/활성/변경 시각·revision으로 보여 준다. 계정 전체 검색/새 계정 생성/전체 비활성화/개인 대화 바로가기는 추가하지 않는다. 사용자 소속 활성 변경은 API-19, 역할은 API-20으로 구분한다.

| 관리자/대상 | 활성 변경/역할 표시 |
|---|---|
| TADMIN → 같은 조직 USER | 소속 활성/비활성 가능; USER→TADMIN 승격/관리자 회수 불가 |
| TADMIN → TADMIN/PADMIN | 변경 버튼 없음; 비활성화로 관리자 회수 우회 금지 |
| 관리 소속 PADMIN → 같은 조직 다른 USER/TADMIN | 허용된 소속 변경, USER↔TADMIN 가능; 전역 계정 변경 아님 |
| 자기 역할/관리 범위/플랫폼 권한 또는 PADMIN 대상 | 변경 불가. PADMIN 부여 UI/API 없음 |
| P-A가 B 선택/직접 URL 사용 | B 관리 소속 없으면 목록/변경 모두 거부 |

저장 중 잠금 → expected_revision으로 변경 → 200 새 현재값/감사 완료를 받으면 “저장됨”. 409면 “다른 변경이 먼저 적용되었습니다.”와 현재값 다시 읽기; 자동 덮어쓰기 없음. 403이면 편집/목록을 비우고 권한 안내. 통신 불명은 현재값 재조회로 확인하며 성공으로 표시하지 않는다.

## 7. UI-04 문서·색인·공유 관리

### 7.1 목록/등록/버전

목록 API-21은 안전한 문서 ID/범위/공개·처리·정리 상태/허용 버전/시각을 표시한다. 개인 문서의 읽기 ACL이 없는 관리자는 **“개인 문서 · 식별번호 …”**로 표시한다. 제목 미제공을 파일명·Job 원문·사용량 기록·오류 내용으로 복원하지 않는다. 운영 권한과 본문 읽기 권한을 별개로 다룬다.

등록 폼: TXT/Markdown UTF-8 파일1개(128KiB/40,000문자 이하), 제목, 조직/개인 범위, 개인 소유자/허용 reader 최대10명. 서버 검사/등록 결과가 최종 기준이다. 개인 소유/reader는 허용된 기존 사용자에서 선택하며 관리자가 운영 편의를 위해 자신을 임의 reader로 추가하지 않는다. 조직 문서는 조직 공개 범위를 설명하고 조직 간 공유는 등록과 별도 승인으로 처리한다.

파일 선택 시 로컬 이름/내용은 등록 폼의 임시 입력이다. 등록 후 읽기 권한이 없으면 이 임시 제목/파일/미리보기도 제거한다. 등록 전 미리보기를 운영 ACL의 우회 캐시로 남기지 않는다. 새 버전은 API-23의 현재 문서 revision과 읽기 조건을 검사하며 기존 owner/범위/readers를 임의 변경하지 않는다. 개인 문서 본문을 못 읽는 운영자는 새 본문 버전 업로드도 불가하다.

client_upload_id는 같은 등록 시도에 유지한다. API-22/23 202는 **“등록됨 · 처리 대기”**이며 검색 가능/색인 완료가 아니다. 응답 불명은 같은 접수 식별자로 한 번만 확인 재전송하는 04 계약을 따른다. 파일/제목만 바꾼 채 같은 ID를 재사용하지 않는다. 파일 크기 오류/타입 오류/검증 실패는 실제 서버 분류에 따라 폼 안에 표시한다.

### 7.2 실제 Job·공개·정리 상태

| 축 | 화면 표시/행동 |
|---|---|
| processing_state / Job queued,running | “처리 대기/처리 중”; validate_source→parse_plan→embed_batches→validate_index→publish 실제 단계만 번역 표시 |
| Job completed | “처리 완료”; 실제 publication_state를 별도로 확인. 완료 자체를 모든 버전/수신 조직 공개로 해석하지 않음 |
| failed/blocked/interrupted | “처리 실패/처리 제한/중단”; 안전한 단계/사유/시각·retry_allowed만 제공 |
| needs_review | “사용량 또는 처리 결과 확인 필요”; 자동/수동 재처리 버튼 비활성; 임의 실패로 바꿔 예약 해제하지 않음 |
| publication_state | 현재 공개 버전/미공개를 별도 표시. 새 버전 실패 시 기존 허용 공개 버전 유지 |
| 삭제/cleanup_state | “접근 차단됨 · 정리 대기/진행/실패/완료”; 삭제 접수와 물리·파생 정리 완료 구분 |

API-25/26 Job 상세는 실제 checkpoint/허용 재처리 여부를 표시한다. 서버가 완료 batch 수를 반환하면 그 값만 표시하고 반환하지 않으면 단계만 표시한다. 시간 기반 100%/고정 성공 알림/자동 타이머를 쓰지 않는다. API-27 재처리는 client_retry_id/expected_revision과 현재 권한·한도 검사 후 접수되며 완료 embedding checkpoint만 재사용한다. Job 취소/강제 완료 API/버튼은 추가하지 않는다.

문서 삭제는 현재 조직/안전한 문서 식별자/현재 버전·신규 접근 차단 효과를 확인하는 동작 후 API-24를 한 번 보낸다. 개인 제목이 비허용이면 확인창에도 숨긴다. 성공 시 접근 차단 상태를 표시하고 정리는 별도로 조회한다. 통신 불명은 문서 상태 재조회; 삭제 성공/정리 완료를 임의 표시하지 않는다.

### 7.3 조직 문서 정확 버전 공유/회수

소유 조직의 organization 문서에서만 현재 허용 공개 버전을 고르고 API-28의 구성된 활성 수신 조직 → API-29 현재 Grant → API-30 승인 순으로 진행한다. 수신 조직 목록 조회는 그 조직 관리 권한/전 조직 본문 접근을 부여하지 않는다. 개인 문서에는 공유 버튼이 없고 직접 API도 거부한다. 수신 조직은 재공유 버튼/승인 권한이 없다.

승인 확인은 소유 조직/안전한 제목·정확 버전/수신 조직을 명시한다. 승인은 정확 버전이며 새 버전 자동 공유 옵션이 없다. D-S v1을 B에 공유해도 B에 미허용 v2/최신 사실을 표시하지 않는다. 회수는 API-31 expected_revision 성공 뒤 비활성 상태로 표시한다. 응답 불명/409는 현재 Grant 재조회 후 판단하고 다른 버전/수신 조직으로 자동 재시도하지 않는다. 과거 인용/진행 실행/Job도 현재 gate에서 차단되는 06 계약을 적용한다.

## 8. UI-05 Agent 설정·운영

고정 general/rules_rag 2개만 목록화한다. 현재 조직의 이름(80문자)/설명(500문자)/기본 지시문(2,000문자), enabled/config_version을 API-32로 읽고 API-33으로 저장한다. 서버의 동일 입력 검사가 최종 기준이다. 모델/키/외부 URL/도구/권한/자유 Agent 생성은 편집 항목이 아니다. 기본 지시문은 관리 설정이며 일반 사용자 Agent 설명 API-06에 포함하지 않는다.

저장 버튼은 편집→저장 중→서버 성공/새 config_version→저장됨 상태로 처리한다. 409면 현재값을 다시 읽고 같은 조직·권한 내에서 재편집한다. 조직 전환/권한 회수 시 편집 초안을 제거한다. 진행 실행의 이미 수락된 config snapshot을 화면 편집으로 바꾸지 않는다.

운영 중지/재개는 현재 조직/Agent/적용 효과 확인 후 API-34 expected_revision을 사용한다. 응답 전 토글을 성공 상태로 바꾸지 않는다. 중지는 신규 호출/후속 허가 단계에 적용하고 rules_rag 색인도 중앙 통제한다. 이미 전송한 공급자 호출의 즉시 종료/0원 보장은 표시하지 않는다. 재개는 공통 중지·한도·불명 예약을 해제하지 않으며 다른 차단 조건이면 계속 제한 표시한다.

## 9. UI-06 조직 사용량·한도

API-36 호출 목록은 기간/operation/real 또는 mock/호출 상태/확인된 토큰·추정 금액/예약·불명/안전한 식별자로 제한한다. 생성뿐 아니라 문서·질의 임베딩/실패 호출도 포함한다. 질문/답변/개인 제목을 추가하거나 usage 행에서 타인 대화로 이동하지 않는다. 기본20건/최대50건을 지킨다.

| 값 | 화면 의미 |
|---|---|
| accounted cost | 확인된 사용량에 근거한 보수 추정 금액; 공급자 최종 청구액 아님 |
| reserved cost | 아직 해제/정산되지 않은 예약; 사용할 수 있는 잔여에서 제외 |
| unknown | “사용량 확인 필요 · 예약 유지”; 0원/무료/정산 성공으로 표시 금지 |
| real/mock | 실제 API 비용 집계와 모의 시험 집계를 별도 표시/합산 금지 |
| allocated/local cap | 상위 배정/조직 운영 제한을 구분. 잔여는 서버값/정의 사용, 화면에서 독립 재계산으로 호출 허가하지 않음 |

API-37 현재값 → API-38 조직 제한 변경(배정 이하, expected_revision) → 성공 후 서버값 표시. 조직 관리자는 승인30,000원/운영상한25,000원 자체를 늘리지 못한다. 관리 소속 PADMIN에게만 **현재 조직**의 상위 배정 편집(API-41)을 제공한다. path tenant와 헤더 tenant가 같아야 하며 전 조직 배정 표를 만들어 범위를 확대하지 않는다.

25,000원 운영상한/5,000원 여유는 승인30,000원 안의 설계값이다. 여유를 추가 예산처럼 표시하거나 임의로 자동 투입하지 않는다. 사용량/한도 미연결은 “조회 연결 전/조회 실패”, 초기화 미완료는 “설정 필요”로 구분한다. 제안 화면의 임의 0원/99%/사용률 수치를 실제 응답처럼 표시하지 않는다. 실제 DB가 초기화되어 조회가 성공한 경우에만 실제 빈 목록/0을 보여 준다.

## 10. UI-07 플랫폼 운영과 최소 응답 보완

공통 합산 조회와 공통 운영 변경은 독립 권한이다. 조직별 본문 조회 없이 프로젝트 합계/예약/불명/현재 공통 상태만 제공한다. 승인30,000원과 운영상한/여유의 의미를 읽기 정보로 표시하며 모델 선택/실시간 가격 수정/정산 수정/추가 예산 승인 기능은 추가하지 않는다.

| 현재 권한 | 화면 |
|---|---|
| PADMIN + global_usage_read만 | API-39 프로젝트 합산/운영 상태 조회; 운영 변경 버튼 없음 |
| PADMIN + global_stop_write만 | 현재 공통 운영 상태/revision과 중지·재개만; 비용 합산 영역 없음 |
| PADMIN + 둘 다 | 합산과 운영 변경 표시; 각각의 API가 현재 권한 재검사 |
| PADMIN이나 두 권한 없음/회수됨 | UI-07 메뉴 숨김, 직접 요청 거부, 이미 열린 데이터 비움 |

**기존 API의 화면 지원 필드 보완안(신규 endpoint 없음):** API-03 `/auth/me`에 서버가 현재 권한으로 계산한 `capabilities.can_view_platform_usage`, `capabilities.can_change_platform_availability`를 추가한다. 후자가 참일 때만 `platform_availability={enabled,revision}`의 비콘텐츠 상태를 포함한다. global_stop_write만 있는 주체가 API-39 비용 조회 권한을 얻지 않고도 API-40의 expected_revision을 확보하기 위한 계약이다. API-39에는 조회 허용 범위의 공통 enabled/revision을 명시한다. 불허 주체에게 상태/revision을 반환하지 않는다.

API-05의 effective_role/can_manage는 조직 관리 메뉴/상위 배정 버튼의 최소 입력이다. PADMIN 관리 소속 조건과 글로벌 permission을 혼합하지 않는다. 위 capability는 UI 표시 힌트이며 권한 증표/캐시된 허가가 아니다. 현재 서버 권한 검사가 최종 기준이다. 변경 전 상태 GET과 PUT 사이 회수/경합이 있으면 403/409를 따라 표시를 정리한다.

공통 중지 확인은 **프로젝트 전체**와 신규/후속 AI 허가 제한 효과를 표시한 후 API-40 한 번 호출한다. 200 current state/revision으로 확정한다. 응답 불명은 권한별 API-03/39로 현재 상태를 재조회하며 자동 PUT 반복 없음. 재개가 기존 Agent/조직 제한/불명 예약을 해제하지 않는다는 실제 상태를 보여 준다.

이 필드 보완은 본 문서의 검토 가능한 설계안이다. D240-08에서 02/04와 통합하고 250 계획/실제 구현 때 반영해야 하며 지금 API 구현이 있다고 표시하지 않는다.

## 11. 변경·접근성·시연 표시의 공통 규칙

모든 관리 변경은 조회/편집/저장 중/저장됨/거부/충돌/결과 확인 필요를 구분한다. 서버 응답 확인 전 성공 알림/토글 확정/업무 완료 카운트를 만들지 않는다. 같은 조직·현재 권한 안에서만 편집값을 보존할 수 있고 조직 전환/권한 변경은 비운다. 실패 폼을 무조건 초기값으로 덮어쓰거나 다른 사용자 새 변경을 자동 병합하지 않는다.

빈 상태는 성공 조회의 빈 결과다. 조회 실패/권한 거부/미연결/미초기화는 빈 상태와 다르다. 민감 API 응답은 no-store 계약을 따르며 화면에서 로그/오류 추적 payload로 원문·질문·답변을 복제하지 않는다. 관리 화면의 직접 URL/복사한 ID도 서버가 검사한다.

라벨/키보드 포커스/버튼 비활성 사유·오류 위치를 제공하고 상태를 색상만으로 구분하지 않는다. 완료/실패 안내는 문구와 함께 표시하며 작성 중 답변이 계속 읽기 위치를 강제로 바꾸지 않도록 한다. 좁은 화면에서도 현재 조직/작업 대상/중지 범위가 보이게 한다. 정식 접근성 인증이나 성능 합격을 이번 문서로 주장하지 않는다.

기존 BNK 제안 화면/PNG/정적 목록·alert·타이머 진행·고정 사용량은 레이아웃 참고만 한다. 현재 원본 자산은 수정하지 않는다. 앱 연결 전 시연은 **“정적 화면 예시 · 업무 처리 미연결”**, 모의 제공자 시험은 **“모의 응답 · 실제 비용 아님”**, 실제 호출은 서버 real 값으로 표시한다. 합성 문서/가상 조직이라는 자료 표시와 real/mock 실행 표시를 분리한다. 합성 자료를 사용해 실제 API를 호출하는 경우도 real 비용이 발생한다.

## 13. D240-08 통합·구현 전달 항목

1. API-03 플랫폼 capability/조건부 availability 및 API-39 enabled/revision 필드를 02 권한/04 응답 명세와 통합한다. global_stop_write가 global_usage_read를 암묵 부여하지 않는 사례를 필수 검사한다. 기존41 endpoint 수는 유지한다.
2. Agent 변경→새 대화 정책에 필요한 대화의 Agent binding을 03/04에 명시한다. 첫 실행 또는 대화 생성의 서버 binding, 후속 실행 다른 Agent 거부/새 대화 유도, 과거 대화 선택 시 해당 Agent 표시를 정한다. 현재 conversation 테이블에 그 필드가 구현되었다고 가정하지 않는다.
3. 관리 문서 제목 미제공/본문 읽기 가능 여부, Job retry_allowed/안전한 사유, 사용량 집계/unknown·현재 배정 필드, real/mock 응답을 04/05/06과 대조한다. 화면이 임의로 제목·진행률·과금·권한을 추론하지 않게 최소 명시 필드를 확정한다.
4. UI-02 완료 본문/이력/근거의 현재 ACL 및 조직 전환 세대 검사, API-11 같은 ID 조회/제한 재전송, 보류/검색 실패/저장 불명/취소 경합을 04/06과 통합한다. 저장 본문 전체 차단을 부분 표시로 완화하지 않는다.
5. 실제 라이브러리/설치 버전/라우터/테스트 도구·컴포넌트/파일 분할은 설계 승인 후 250 기능 계획에서 고정한다. 화면 spec만으로 런타임/성능/보안 통과를 표시하지 않는다.
