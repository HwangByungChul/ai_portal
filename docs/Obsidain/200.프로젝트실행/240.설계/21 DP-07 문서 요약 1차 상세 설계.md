# DP-07 문서 요약 1차 상세 설계

## 결정할 첫 묶음

추천은 단일 게시 문서의 **원문 발췌 요약 → 별도 재생성 → Markdown 내려받기**다. 기존 저비용 모델이 후보 ID를 선택하고 서버가 해당 원문만 표시한다. 2026-10-07 사용자 설계 승인 후 구현 진행 중이며, 이 문서는 개발 완료나 수용 증거가 아니다.

| 접근 | 장점 | 제약 | 선택 |
|---|---|---|---|
| 원문 발췌 요약 | 원문 밖 숫자/기한/담당자 생성 방지, 출처 정확성 검증과 비용 제한 용이 | 자연스러운 재서술·다문서 종합 부족 | 1차 권고 |
| 자유 재서술+사실 검증 | 읽기 좋은 요약과 번역으로 확대 가능 | 추가 검증·오류 대응 및 모델 비용 필요 | 후속 |
| 여러 문서 분할·통합 요약 | 긴 문서와 종합 업무 지원 | 다단계 비용·취소·coverage·회수 계약 복잡 | 후속 |

후속 번역·자유 재작성·PDF 출력은 DP-07 잔여 범위로 유지한다. PPTX/OCR은 사용자가 보류한 DP-06 잔여 범위다. 기존 일반 대화와 규정 RAG는 유지한다.

## 화면 흐름

업무 공간에 ‘문서 요약’을 추가한다. 현재 읽기 허용된 게시 문서 목록에서 제목·버전을 선택하고 핵심 항목3/5개를 지정한다. ‘요약하기’ 후 접수/처리 중/완료/근거 부족/차단 상태를 표시한다. 처리 중 취소가 가능하며 결과 검증 전 모델 원문을 화면으로 streaming하지 않는다.

완료 화면은 ‘원문 발췌 요약’ 표시, 실제 항목 수, 각 원문 인용·위치·버전, ‘다시 요약’, ‘Markdown 내려받기’를 제공한다. 재생성 전 ‘같은 버전으로 새 실행을 만들며 실제 모드에서는 비용이 발생할 수 있습니다’ 안내를 표시한다. 동일 결과가 나와도 오류로 간주하지 않는다. 새 버전을 자동 선택하지 않는다.

조직/로그인 세대 변경 시 실행·결과·선택 문서·Blob URL을 폐기한다. 늦은 응답은 현재 조직에 표시하지 않는다. 관리자에게 개인 요약을 노출하는 목록은 만들지 않는다. 키보드와320px 화면을 검증한다.

## 처리 경계

1. 요청에서 tenant/user/role/prompt/model/금액/외부 URL을 받지 않는다. 서버 인증 컨텍스트, 현재 조직, 기존 승인된 설정이 기준이다.
2. 현재 게시·원문 권한과 실행 모드가 일치하는 정확한 문서/버전 한 개를 확인한다. 서버가index_id/source SHA/parser revision을 결합한다.
3. 저장된 canonical을 SHA 검증 후 읽고 제목+전체 텍스트 최소 정책을 재검사한다. 원문 파일의 정책 검사 실패는 외부송신 전에 차단한다.
4. 기존 오프라인 document plan/evidence에서 완전한 원문 단위를 구성한다. quote와start/end·행 범위가 일치해야 한다. 구조 레이블만 있는 단위는 제외하고, PDF/DOCX/XLSX는 검증된 origin 위치에 대응되는 실제 내용 단위만 후보로 인정한다.
5. 후보 전체 최대 128개, 서버 system instruction+제목+후보 전체 입력6,000토큰 이하. 한도 초과 시 SUMMARY_LIMIT_EXCEEDED로 거부한다. 후보를 앞부분만 잘라 성공으로 처리하지 않는다. 후보 0개이면 insufficient_evidence로 저장하고 모델 호출 0회다.
6. 모델에는 후보 ID와 정확한 인용만 보내고 `{"selected_ids":["U0","U3"]}`만 허용한다. 문서 내 지시문은 데이터로 취급하며 도구/네트워크 기능을 부여하지 않는다.
7. 반환은 엄격한 JSON 객체, selected_ids 키 한 개, 유일한 기존 ID 최대 요청 3/5개를 검증한다. 빈 배열은 근거 부족이다. 추가 텍스트·중복·없는 ID·타입 오류·512 토큰 초과는 SUMMARY_OUTPUT_INVALID. 자동 재호출하지 않는다.
8. 서버가 선택된 원문을 원문 순서로 렌더링한다. 모델이 작성한 문장·라벨은 저장·표시하지 않는다. 결과+제목 최소 정책을 검사한다. 원문/정책/출력 버전과선택ID·정확한quote/hash/위치 snapshot을 봉인한다.
9. 저장 직전에 현재 권한·worker claim·실행 상태를 재확인하고 결과/근거/완료 상태를 원자적으로 저장한다. 조회·원본·재생성·내려받기는 다시 현재권한을 검사한다.

이 최소 정책은 document-ingest-v1 검사의 재사용 및 summary-v1 호출 순서 계약이다. 완전한 개인정보 탐지/프롬프트 공격 탐지·조직별 정책 관리 완료로 표현하지 않는다. 정책 검사는 원문 offset을 변경하지 않는다. 여러 인용과 레이블의 조합 결과도 다시 검사한다.

## API 계약 — 신규 제안

- `POST /api/v1/document-summaries`: `{client_send_id: UUID, document_ref: {document_id: UUID, version_id: UUID}, bullet_count: 3|5}`. 추가 필드 금지. 새 요청201, 동일 요청 재접수200. 응답은run_id/state/revision/replayed이며 본문을 접수 응답에 포함하지 않는다.
- `GET /api/v1/document-summaries/{run_id}`: 현재 읽기 가능한 자기 실행의 상태와 검증된 결과·coverage·선택 출처. 타 사용자/조직404. 문서 회수 후 본문/제목/인용을 제공하지 않는다.
- `POST /api/v1/document-summaries/{run_id}/regenerate`: `{client_send_id: UUID, expected_revision: int}`. completed 또는 insufficient_evidence인 자기 실행만, 같은 정확한 버전으로 새 실행/부모 연결. 실패/취소는 원래 요청을 자동 재전송하지 않고 새 요약 요청을 이용한다. 동일ID+다른요청409.
- `POST /api/v1/document-summaries/{run_id}/cancel`: `{expected_revision: int}`. 기존 revision/fencing/원장 취소 계약 유지.
- `GET /api/v1/document-summaries/{run_id}/export?format=md`: 완료·봉인 결과만 즉시 재검증하여 제공. 파일명summary.md, text/markdown;charset=utf-8, attachment, no-store, nosniff. 임시 공개 URL/장기 export 캐시를 생성하지 않는다.
- `GET /api/v1/document-summaries/{run_id}/evidence/{ordinal}/source`: 출처 ordinal0~4, 현재 자기 실행+원문권한·두SHA 확인 후 기존 형식의 정확한 원본 제공. URL은opaque ID만 포함한다.

오류: 요청422, 비허용/회수404, revision/ID 충돌409, 실행/요약한도422 또는 기존 quota 코드, 접수속도429, 정책검사장애503. 정책 거부422. 사용자 메시지는 제한 사유와 재시도 가능 여부만 제공하며 매칭 개인정보나 내부 경로는 반환하지 않는다.

## 실행·데이터 설계

첫 묶음은 새 Agent Registry를 만들지 않고 기존 rules_rag의 사용 가능 설정/조직 예산·모드·저비용 생성 permit을 사용한다. 화면에는 요약이 규정 RAG 설정의 활성화/한도에 따른다는 안내를 제공한다. DP-09 이후 동적 자산으로 분리할 수 있다.

규정 답변과 혼동하지 않도록 portal.runs에 서버 전용 `task_kind`를 추가한다: 기본chat, 추가document_summary. 기존 행은chat이다. summary admission은전용 함수로만 가능하며 클라이언트는task_kind를 지정할 수 없다. 기존 chat admission/실행/규정finish는chat만 허용하도록 신규 migration에서 검사한다. 범용 chat API를 통한summary 대화 재사용·표시 우회를 차단한다.

신규 `portal.summary_requests`는(tenant_id,run_id) 기본키와run FK, owner/document/version/index/source SHA/bullet_count/request_hash/parent_run_id/policy_revision/parser_revision을 보관한다. parent는 같은tenant·owner·task만 허용한다. 새 summary는 새conversation+run을 만들고 기존 대화 이력을 모델로 보내지 않는다. 요청 identity는kind+정확한 문서버전+개수+부모+프로토콜 revision을 포함한다. 같은send는chat/summary 사이에서도 충돌을 검사한다.

신규 `portal.summary_evidence`는(tenant_id,run_id,ordinal) 기본키, 기존rag.evidence FK, 원문 SHA·quote_snapshot·위치 네 필드·quoteSHA를 봉인한다. 기존 규정answer_evidence/relation_id/rag_finish 계약은 유지한다. summary 봉인은 실제rag.evidence에 존재하는 원문 quote/hash/offset과 선택 후보를 확인하며 관계 존재를 요구하지 않는다. 결과 내용은서버 발췌 렌더러가 만든 값과 일치해야 한다.

summary 전용 admission/claim source 확인/call reserve/finish/read/export SQL capability를 만든다. 중앙call_dispatch/call_meter와worker epoch·heartbeat·cancel·recovery를 유지한다. generation operation은기존generate_rag를 재사용하되task_kind별 허용을 명시하여요약에 embed_query를 허용하지 않는다. 새 summary 실행은생성step1회이며 확인되지 않은송신/사용량은unknown으로 보존한다. 채무를삭제하거나0원으로 치환하지 않는다.

정책 함수는 고정search_path·ai_policy_executor 소유·PUBLIC execute회수·필요역할만 grant를 적용한다. summary 테이블은owner+tenant RLS 및현재문서권한을 사용하며ai_meter는본문을읽지 않는다. 현재32개테이블의원래 열/행 및SQL 000~024를 보존하는지검증한다. `025_document_summary_control.sql`은예약명이며아직 생성/적용하지 않았다. 새constraint/함수교체 목록은구현계획에서실제정의와맞춰열거한다.

## 단계별 다음 수행과 종료 기준

220·230을확인하고이240설계에대한사용자검토후상세 구현 계획을작성한다. 구현순서는요약정책·순수검증기 → disposable DB의전용capability/격리 → executor/원장 → 화면 → module시험 → 회귀/인수전달이다. 테스트 DB를쓰는서버/화면검증은순차로실행해역할/비밀번호 충돌을피한다. 순수검증기시험과빌드는독립으로실행가능하다.
