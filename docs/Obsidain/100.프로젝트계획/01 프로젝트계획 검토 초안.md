# 프로젝트계획 검토 초안

## 현재 확정된 사용자 지시

- 개인적으로 AI 플랫폼을 학습·MVP 구축하며 향후 유사 사업 제안·시연에 활용한다.
- 완료 목표: **2026-10-31**. 사용자 2026-10-04 지시 반영.
- 가용시간: **주 20시간 이상**. 기본 계획은 주 20시간·4주·80시간으로 검토한다.
- 모델 환경: **OpenAI API 사용 예정**. 사용자에게 제공자 표기를 확인했다. 10월 API 실습 예산은 **최대 30,000원**으로 확인했다. 구체 모델·계정/API 사용 가능 여부는 후속 기술 검토한다.
- BNK 그룹 공동 생성형 AI 플랫폼 자료를 사업 범위 참고자료로 사용한다.
- 기존 GraphRAG AI Agent를 재사용 후보로 검토한다. 사용자·관리자 화면과 연결하는 방향이다.
- 멀티테넌트가 중요한 검토 항목이며 필수 범위로 반영한다. 1차 MVP는 공통 서버에서 조직별 데이터·권한·정책의 **논리 격리 및 우회 차단 검증**을 수행한다. 조직별 독립 실행환경은 1차 범위에 포함하지 않는다.
- API G/W 제품 도입을 전제로 하지 않는다. 오픈 프레임워크 또는 자체 공통 처리 방안을 검토한다. 앞서의 제품 도입 방향은 최신 지시로 대체한다.
- 프로젝트는 `/Users/jwpios/antigravity/202610_AI 플랫폼`에서 진행한다. 산출물 폴더의 단계 순서로 검토한다.

최초 검토 당시 앱 소스와 Git 저장소는 없었다. 현재 앱은 미구현이며 통합 계획서의 로컬 문서 버전 기록을 위해 Git를 초기화했다. 기존 구조와 검토 자료는 준비되어 있다. 설계·구현 방식은 아직 확정되지 않았다.

## 계획 단계에서 정할 것

전체 과제를 포털/운영 Core, API 공통 진입, AI 공통 호출, Knowledge/GraphRAG, 버전/승인으로 나눈다. 단일 문서에서 모든 기능의 상세 설계를 완료하지 않는다. 100 단계에서는 첫 MVP 범위·우선순위·추진 방식·검증 목표를 정하고 210/220/230에서 구조·요구·재사용을 구체화한다.

현재 범위 후보는 로그인·조직 선택·Agent 선택·채팅/이력·문서/근거, 관리자 사용자/역할·문서/색인·Agent 중지·사용량/한도다. 최신 멀티테넌트 지시를 이 흐름의 공통 전제로 추가한다. 자유 Canvas·기업 SSO·GPU 운영·전체 Marketplace는 후속 후보이며 최종 포함 여부는 계획 검토에서 결정한다.

## API G/W 제품 없이 진행하는 세 가지 접근

| 접근 | 구성 | 장점 | 직접 책임질 부분·부담 | 권고 조건 |
|---|---|---|---|---|
| A. FastAPI 공통 진입 모듈 | 업무 API와 같은 배포, Middleware/Dependency/Router로 책임 분리 | Python/GraphRAG 경로 활용, 개인 개발의 배포 부담 낮음 | 조직 확인·권한·요청 제한·감사·오류를 직접 설계/시험. 독립 서버 간 라우팅은 없음 | **논리 격리 우선 MVP의 추천안** |
| B. 별도 FastAPI 진입 서버 | 외부 진입 서버→조직별/공통 backend | 제품 없이 라우팅·서버 경계·조직별 실행환경을 직접 학습 | Proxy 스트리밍·취소·Timeout·인증 문맥·내부 API 우회 차단을 구현, 배포 단위 증가 | 독립 조직 환경의 라우팅 시연이 중요할 때 |
| C. Spring Cloud Gateway 프레임워크 | Spring 기반 진입 서버 + FastAPI/GraphRAG | Java/Spring 경험 활용, 라우팅·필터 프레임워크 활용 | Java/Python 두 환경, 조직 정책·데이터 ACL은 별도 구현 | Spring 중심 기업형 구조를 학습할 때 |

A는 일반 목적 Gateway 제품의 기능 전체를 대체한다고 주장하지 않는다. B는 자체 Proxy 구현의 범위를 명확히 제한해야 한다. C는 상용 Gateway 제품 구매 없이 사용할 수 있는 프레임워크 후보지만 사용자 표현의 ‘솔루션 도입 없이’를 별도 Gateway 배포도 최소화하려는 뜻으로 해석하면 A가 더 적합하다.

현재 추천은 A로 기본 흐름을 검증한 후 필요하면 B/C로 공통 진입을 분리하는 것이다. 조직별 독립 환경을 첫 MVP부터 요구한다면 B/C 우선으로 다시 평가한다. 특정 접근을 아직 승인된 설계로 기록하지 않는다.

## 멀티테넌트에서 공통으로 필요한 범위

테스트 조직 A/B와 명시적으로 공유 승인된 공통 자산을 준비한다. 공통 자산은 모든 조직을 한꺼번에 검색하는 권한이 아니다. 초기 조직 수는 검토 가정이며 실습 규모 결정 시 확정한다.

1. 인증된 사용자의 활성 조직 소속과 역할을 서버에서 조회해 요청 문맥을 만든다. 클라이언트의 tenant_id/Header만 믿지 않는다.
2. 사용자 메뉴·Agent·문서·대화·원장·관리 기능에 조직 범위를 적용한다. 메뉴 숨김과 API 권한 검사는 별도 검증한다.
3. 벡터 검색뿐 아니라 Graph 탐색·근거 조회·원문 다운로드·삭제에 같은 조직/개인 ACL을 적용한다.
4. 비동기 Job·재시도·캐시·저장 경로에도 조직 정보를 유지한다. 서로 다른 조직 요청을 동시에 처리해 문맥 혼입을 시험한다.
5. 조직별 요청수 제한, AI 동시 실행·토큰/비용 한도, 중지 정책과 실행 감사 이력을 연결한다. HTTP 요청 제한과 AI 사용량 예약/정산은 별도 책임이다.
6. 관리자도 그룹/조직 관리 범위를 검사한다. 조직 관리자는 다른 조직의 사용자·모델 정책·문서·사용량을 변경할 수 없다.
7. 조직 전환 후에도 대화와 Agent 실행은 소유 조직을 유지한다. 조직 불일치와 권한 없는 직접 URL/ID 요청은 차단한다.

이 기능은 FastAPI나 Gateway 프레임워크를 설치하면 자동 확보되는 기능이 아니다. 저장소·업무 API·GraphRAG의 구현과 시험이 필요하다.

## 확인된 격리 수준과 다음 확인

사용자는 2026-10-04 **논리 격리 우선**을 선택했다. 조직별 서버·DB·저장소를 물리적으로 분리하는 실행환경 시연은 후속 범위다. 공통 DB의 조직 식별·권한 강제 방법과 방어 계층은 210/240에서 비교·설계한다. 공통 서버를 사용하더라도 계정·문서·대화·검색·근거·관리 API의 우회 차단은 필수다.

이 조건에서는 **A. FastAPI 공통 진입 모듈**을 권고한다. Middleware는 요청 ID·관측 등 공통 처리를, 인증 Dependency/서비스는 조직 소속·자원 권한을 담당한다. 별도 Reverse Proxy와 서비스 간 라우팅 구현은 1차 핵심 범위에서 제외하는 제안이다. 이는 추천안이며 기술 설계 승인과 구분한다.

주당 가용시간은 20시간 이상으로 확인했다. OpenAI API 사용 예정으로 확인했다. 10월 API 실습 예산은 최대 30,000원으로 확인했다. 다음은 MVP 범위·추진 방식·완료 기준의 항목별 검토다. 완료 목표는 2026-10-31, 계획 가용시간은 80시간이다. 세부 공수와 실현 가능성은 모델 환경·재사용 Gap과 첫 반복의 실측으로 보완한다.
