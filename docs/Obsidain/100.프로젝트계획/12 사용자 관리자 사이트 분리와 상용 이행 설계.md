# 사용자 관리자 사이트 분리와 상용 이행 설계

기준: [[100.프로젝트계획/11 포털 상용화 기반 UI 통합 상세 실행 계획]], [[200.프로젝트실행/240.설계/23 포털 UI UX 확정과 사이트 분리 검토]].

## 현재 구현 경계

사용자 `/home`과 관리자 `/admin`·`/admin/approvals`는 각각 독립 메뉴·기본 홈을 가진다. 관리 페이지는 실제 tenant.can_manage와 플랫폼 capability를 확인하고 API/DB에서도 현재 권한을 검증한다. 현재 빌드·개발 출처는 하나다. 경로 분리를 별도 앱·배포 완료로 표시하지 않는다.

## 권고 상용 구조와 전환 순서

| 단계 | 구현·검증할 내용 | 완료 증거 |
|---|---|---|
| 1 · 현재 앱 UI 경계 | 사용자 메뉴/관리 메뉴 분리, 홈·승인 연결, 기존 직접 URL 유지 | 로컬 실제 API 기반 화면·권한 시험 |
| 2 · 코드·빌드 분리 | `apps/user-web`, `apps/admin-web`, `packages/ui`, `packages/api-contract`로 기존 컴포넌트를 이동. 인증·API 클라이언트는 공유 계약을 사용하되 관리 화면은 user-web 번들에서 제외 | 별도 lock 적용 검토 후 두 빌드, 사용자 번들의 관리 코드 제외, 양쪽 회귀 |
| 3 · 인증·출처 분리 | 사용자와 관리자 각각의 SSO/OIDC 클라이언트, 사이트별 서버 세션/BFF, 관리 MFA와 권한 재확인 | 실제 IdP 시험 환경의 로그인/로그아웃/권한 회수/CSRF/SSO 실패 시험 |
| 4 · 환경·배포 분리 | 예시 `ai.example.com`과 `ai-admin.example.com`의 독립 릴리스, 공통 업무 API와 조직 경계, 별도 UI 배포·복구 | 실제 소유 도메인/TLS/CI·관측·복구 증거 |
| 5 · 상용 운영 진입 | 사용자·승인자 역할 검토, 조직 경계와 감사 보존, 장애·부하·백업복원·비용한도 | 승인된 운영 환경의 수용 시험과 출시 기록 |

새 경로·정적 호스트만 만들어 공통 쿠키를 임의 공유하지 않는다. 사용자·관리자 JS에 키·DSN·승인 권한을 넣지 않는다. 사용자 번들의 관리 코드 제거는 공격 표면을 줄이는 조치이며 서버 권한 검사를 대체하지 않는다.

## 인증·API 계약

- 브라우저는 각 사이트의 같은 출처 `/api`로만 호출한다. BFF는 공개 클라이언트가 제출한 user_id/role/tenant claim을 신뢰하지 않고 인증된 서버 주체를 API에 전달한다.
- OIDC authorization code + PKCE, 정확 redirect URI, state/nonce, 만료·토큰 검증과 MFA 정책은 선택된 IdP 계약에 맞춰 구현·시험한다. 토큰을 localStorage에 저장하지 않는다.
- 사이트별 host-only HttpOnly/Secure 세션을 권고한다. 공통 SSO는 IdP 재인증 세션으로 제공하고 앱 간 세션 쿠키 공유와 구분한다.
- 현재 backend의 단일 `Settings.origin`·local 5173 강제 계약을 운영 출처 목록으로 단순 확장하지 않는다. 각 사이트가 어느 세션/클라이언트와 연결되는지 서버에서 검증하는 계약과 시험을 먼저 만든다.
- 관리자 서버는 일반 사용자 세션·권한을 승인 권한으로 승격하지 않는다. 인증된 조직 관리 PADMIN과 요청자 분리 검사를 결정 직전에 실행한다.
- 권한 회수·로그아웃은 UI 가리기와 서버 거부를 함께 시험한다. 브라우저 BroadcastChannel 통지는 같은 출처에 한정되므로 다른 출처 logout은 서버/IdP 계약이 필요하다.

## 현재 승인 업무의 의미

이번 ‘배포 승인’은 고정 Agent `general`/`rules_rag`의 **이름·설명·기본 지시문** 변경안을 승인 후 현재 조직 운영 설정에 반영하는 일이다. 서비스 컨테이너·새 코드·새 모델·도구·MCP·키·외부 URL 배포를 의미하지 않는다. 이를 확장하려면 자산 버전·허용 도구·모델 계약·자동 평가·스테이징·롤백을 별도 요구로 추가한다.

요청 스냅샷은 승인 전 운영 설정을 바꾸지 않는다. 승인과 설정 반영·감사는 한 DB transaction이다. 운영 enabled와 한도·비용·예약은 그대로 유지한다. 긴급 중지/재개는 기존 운영 제어이며 설정 버전을 증가시키므로 과거 기반 요청의 승인은 차단된다. 롤백은 과거 스냅샷의 새 요청과 다른 승인자의 승인으로 수행한다.

## 상용화 전 필수 전환 항목

| 항목 | 현재 상태 | 필요 작업 |
|---|---|---|
| 계정·SSO | 합성 계정·프로젝트 전용 세션 | 실계정 수명주기, IdP 연결, MFA, 접근/퇴사 회수 |
| DB | 표식·고정 포트·fixture 명칭 검증 | 운영 DSN/역할/이행 계정의 별도 profile, 기존 보호를 완화하지 않는 운영 경계 시험 |
| 모델·비용 | 기존 mock/real 구분·원장 | 운영 모델 계약/가격/한도 승인과 관측. 이번 검증은 유료 호출 없음 |
| 문서 격리 | 기존 macOS 처리 sandbox | 운영 OS의 파서 격리·파일 검사·자원 제한·침해 시험 |
| 승인 역할 | 기존 조직별 PADMIN | 실제 업무 분장에 맞는 전용 승인 권한·부재 대체·자가 승인 금지 유지 |
| 검증 근거 | 입력 스키마·버전·현재 권한 | 실제 평가셋·개인정보/보안 검토 결과·승인 체크리스트·근거 파일 버전 |
| 이력·관측 | 저장된 승인/기존 감사 | 보존·접근·위변조 탐지·민감값 제거·운영 알림·상태 지표 |
| 출시·복구 | 로컬 build/시험 | CI gates, 보호 배포, DB 백업/복원/호환 이행·릴리스 롤백 |

**착수에 필요한 외부 정보:** 운영 IdP·등록된 SSO 클라이언트, 소유 도메인·TLS와 배포 환경, 운영 DB·비밀관리, 승인자 업무 권한·로그 보존 정책. 이 정보가 없는 단계는 설계로 기록하며 연동 완료로 표시하지 않는다. 현재 로컬 환경과 비밀 설정은 초기화하거나 임의 운영 환경으로 전환하지 않는다.

## 출시 판단

화면과 Agent 설정 승인 기능은 상용화를 위한 기능 기반이다. 기존 학습용 fixture DB·모의 제공자를 운영 구성으로 바꾸는 것은 별도 단계다. ‘build 성공’과 ‘상용 서비스 출시 가능’을 구분하고, 위 환경·인증·복구·부하 증거가 확보되기 전 운영 공개 배포로 승격하지 않는다.

## 2026-10-12 · 2단계 독립 앱/빌드 완료

초기 “하나의 빌드” 문장은 이전 단계의 이력이다. 지금은 사용자·관리자 앱 진입과 import 그래프·배포 산출물을 분리했다. 같은 개발 출처/기존 Origin/쿠키 계약을 유지한다. [[200.프로젝트실행/250.구현/22 사용자 관리자 독립 앱과 빌드 분리 구현 결과]]과 [[200.프로젝트실행/280.통합시스템테스트/23 독립 앱 빌드 경계와 통합 검증 결과]]를 현재 코드·검증 상태로 따른다. SSO/별도 출처/운영 배포는 미완료이며 IdP 제품·테스트 연동 여부를 확인한 뒤 3단계를 진행한다.

## 2026-10-12 · 도메인 없는 포트와 환경 계약 적용

사용자 요청에 따라 local/dev/tb/prd 공개 설정을 파일로 관리하고 local user5173/admin5174/API8000을 검증했다. [[100.프로젝트계획/14 환경별 설정 관리와 local 포트 분리 실행 계획]], [[200.프로젝트실행/250.구현/23 환경별 설정 관리와 local 포트 분리 구현 결과]], [[200.프로젝트실행/280.통합시스템테스트/24 환경 설정과 두 포트 통합 검증 결과]]. 이전 같은 출처와 단일 Origin 설명은 이력이다. local만 두 trusted origins의 개발 공통 세션을 허용하며 외부환경의 사이트 세션 계약을 단순 allowlist 확장으로 대체하지 않는다. 도메인이 없어도 실제 HTTPS IP+port 계약으로 환경 주소를 마련할 수 있으나 현재 dev/tb/prd 주소는 미확정/실행 차단이다. 상용 runtime과 운영 DB/SSO 수용 작업은 남아 있다.

## 2026-10-12 · 상용화 요구 해석 정정과 전체 기능 개발 재검토

사용자는 상용화 요구가 즉시 운영환경 전환이 아니라 제안 기능을 실제 서비스 오픈 수준으로 구현하라는 뜻이라고 정정했다. [[200.프로젝트실행/230.분석/09 전체 기능명세서 기준 개발 완료 여부 검토 보고서]]와 [[200.프로젝트실행/230.분석/10 전체 화면과 기술요건 구현 대조표]]에서 원본F60/IA150/T62·BR15/TC25를 현재 코드/기존검증과 대조했다. F전체완료 인정0/부분31/미구현29(이전 제외거버넌스11 포함), 기존F49는부분31/미구현18이다. 좁은 DP03/04/05 등 실제 구현 완료를 부모F전체완료와 구분한다. 다음은 기능 잔여 중심으로 DP09 동적자산→DP10 카탈로그/DP13 모델→DP11 Builder→DP12 일반승인→연계/Workflow/업무Agent를 진행하는 제안이다. 실제 SSO/운영환경은 필요한 기능 수용과 마지막 연동 과제로 관리하며 모든 기능개발의 선행 대기 이유로 사용하지 않는다. 기존 화면 A/A+B·브랜드·포트 설정 유지, 거버넌스 제외·PPTX/OCR 보류 유지. 이번은 검토 보고이며 신규 제품 개발/배포를 수행하지 않았다.

## 2026-10-12 · SSO 인증 시스템 선정

사용자가 IdP를 Microsoft Entra ID로 지정했다. [[25 Microsoft Entra ID 선정과 SSO 연동 검토]]에 현재 구성·OIDC 설계안·환경별 필요한 식별자/주소·테스트 환경 미확인을 기록했다. 이전 IdP 제품 미정은 이번 결정으로 해소되었으며 테스트 연동·사이트별 서버 세션·SSO 구현/기관 수용 완료는 아니다. 계열사의 디렉터리 모델·MFA/CA·테스트 앱 등록 사용 가능 여부는 남아 있다. 기능 우선 개발 순서는 계획15를 유지한다.
