# 포털 상용화 기반 UI 통합 상세 실행 계획

> 실행자는 본 계획과 확정 설계를 함께 읽고 작업별 체크리스트와 시험 결과를 갱신한다. 사용자 지시에 따라 이 대화에서 순차 실행한다. 계획 작성은 운영 배포 승인이나 상용 서비스 준비 완료를 의미하지 않는다.

**Goal:** 사용자 A 홈, 관리자 A 운영 홈과 B 승인·검증을 실제 플랫폼에 연결하고 AI 에이전트 배포 승인·이력·접근 경계를 구현한다.

**Architecture:** 기존 React와 FastAPI/PostgreSQL을 재사용한다. 세션·조직 세대·서버 권한·DB RLS를 유지하며 변경 요청 스냅샷과 실제 운영 설정을 분리한다. 사용자·관리자 진입은 먼저 동일 출처의 별도 경로로 구성하고 독립 빌드·상용 출처·SSO는 인증 계약과 운영 환경이 준비되는 단계에서 전환한다.

**Tech Stack:** 현재 lock의 React 19.3.0, TypeScript 7.0.2, Vite 8.3.2, Playwright 1.63.0, 기존 FastAPI/Pydantic/psycopg/PostgreSQL. 이번 작업에서 버전을 갱신하거나 새 런타임 의존성을 추가하지 않는다.

**Spec:** [[200.프로젝트실행/240.설계/23 포털 UI UX 확정과 사이트 분리 검토]]. 진행 결과: [[400.프로젝트관리/02 포털 UI UX 작업 기록]].

## Global Constraints

- 명칭 ‘생성형 AI 플랫폼’, 사용자 A안 업무 허브 홈, 관리 A 운영 홈/B 승인 목록·상세 패널.
- 2026-10-11 사용자 추가 지시: 추후 실제 상용화 가능한 구현. 학습·시연 전용 구현을 제품 완료로 표시하지 않는다.
- 승인 첫 대상: **AI 에이전트 배포**. 문서 게시 승인을 이 단계에 혼합하지 않는다.
- TADMIN/PADMIN의 현재 조직 관리 권한으로 요청·조회, 해당 조직을 관리하는 PADMIN으로 승인·반려. 요청자 본인 승인은 금지한다. PADMIN의 전체 조회 권한만으로 다른 조직 승인 권한을 만들지 않는다.
- 기존 주체·조직·세션 검증, CSRF/Origin, 스냅샷·현재 권한·세대 정리, 비용·예약·불명 사용량 보존.
- 모의·실제 집계를 분리하고 화면에서 청구액·전체 건수·시간 추이·장애·감사 로그를 추정하지 않는다.
- 비밀번호·키·DSN·CSRF·지시문·본문을 공개 로그·증거에 넣지 않는다. 기존 `.runtime` 사적 증거 정책을 따른다.
- 기존 000~025 SQL과 원장·문서 데이터는 보존하고 새 migration만 추가한다. 검증은 소유 표식 있는 폐기용 DB. 기존 DB 초기화·seed 반복 금지.
- 등록된 실제 모델 키를 시험에 전달하거나 유료 호출하지 않는다.
- 사용자 지시와 현재 변경 외 미추적 문서를 임의 커밋하지 않는다. 변경 전 백업·파일 지문과 변경 목록을 보존한다.

### P3 · Agent 배포 승인 영속 API와 B 패널

Create: `src/backend/migrations/026_agent_deployment_approval.sql`, `app/approvals/routes.py`, `repository.py`, `__init__.py`, `tests/test_agent_approvals.py`; frontend `ApprovalsPage.tsx`.
Modify: `app/main.py`, `app/operations/repository.py`, `AgentSettingsPage.tsx`, `types.ts`, `api.ts`; 관련 기존 시험.

API contract:

```text
POST /api/v1/admin/agent-deployments
{client_request_id:UUID,agent_key:'general'|'rules_rag',expected_revision:int,
 name:string(1..80),description:string(0..500),instructions:string(1..2000),reason:string(1..500)}
→ 201 새 요청 / 200 동일 요청 재전송. 요청 내용 불일치 409.
GET /api/v1/admin/agent-deployments?status=pending|approved|rejected&cursor=UUID&limit=20
→ {items,next_cursor}; 조직·현재 관리 권한 고정, 기본 전체 상태.
GET /api/v1/admin/agent-deployments/{id}
→ 요청 당시 스냅샷, 현재 버전, 검증 항목·가능 행위·처리 이력.
POST /api/v1/admin/agent-deployments/{id}/decision
{decision:'approve'|'reject',expected_revision:int,comment:string(1..500)}
→ 요청 revision 증가·결정 저장. 승인 시 같은 transaction에서 기존 config_version CAS 및 설정 반영.
```

스냅샷에는 이름/설명/지시문과 기반 운영 버전을 봉인한다. 요청 편집·수정 API를 만들지 않는다. 반려한 내용은 새로운 UUID/새 스냅샷으로 재제출한다. 구조 검증 결과는 스키마·현재 권한·버전 일치이며 모델 품질·보안 심사 완료로 표시하지 않는다. 자동 승인·자동 LLM 호출 없음.

DB: 요청 테이블은 ai_owner 소유·FORCE RLS. ai_web/index/meter 직접 읽기·쓰기 금지, ai_policy_executor의 고정 함수만 허용. 기존 `operations_authorize`를 재사용하여 현재 역할과 잠금을 재검증한다. 요청자≠승인자, 상태 pending, 기반 버전·expected_revision 일치 검사를 transaction 안에서 수행한다. 제출 UUID 재전송은 중복 배포/감사 없이 기존 요청 반환. 결정 재전송은 동일 승인자·결정·의견에 한해 기존 처리 결과 반환, 다른 입력은 409.

승인 우회 방지: 기존 직접 Agent 설정 변경 RPC의 공개 경로를 승인 필요 409로 차단하고 승인 함수만 내부 설정 변경을 호출한다. 기존 Agent 중지/재개는 운영 제어로 유지하며 버전이 증가하므로 오래된 배포 요청은 승인할 수 없다. 승인으로 운영 중지를 해제하지 않는다. 기존 배포 설정을 되돌리려면 이전 스냅샷을 새로운 요청으로 제출·타인 승인한다.

- [x] 요청·결정·CAS·감사 원자 저장, 실패 시 전체 rollback.
- [x] 일반 사용자/다른 조직/권한 회수/자기 승인/직접 RPC 우회/중복/버전 충돌/감사 실패 시험.
- [x] B 목록·상세: 상태 필터, 검색(현재 페이지 범위 표시), 더 보기, 검증/변경/이력, 승인·반려 의견.
- [x] HTTP 401/403에서는 데이터를 비우고 권한 재확인, 409는 다시 조회 후 사용자 재판단, 변경 API 자동 재시도 금지.

검증: `.venv/bin/python -m pytest tests/test_agent_approvals.py tests/test_operations.py -q`; `npm run test:e2e -- tests/portal-ui.spec.ts tests/auth-tenants.spec.ts tests/chat-operations.spec.ts`. 실제 Agent 새 설정을 다음 run snapshot이 읽는 계약은 기존 실행 시험과 함께 확인한다.

## 3. 검증 사례와 실행 운영

신규 승인 API 시험 예:

```python
request = submit_as('A-ADM', expected_revision=1)
assert operational_agent_version() == 1
assert decide_as('A-ADM', request, 'approve').status_code == 403
assert decide_as('P-A', request, 'approve').status_code == 200
assert operational_agent_version() == 2
assert repeat_same_decision_as('P-A', request).status_code == 200
```
